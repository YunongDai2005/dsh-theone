# 执行边界：TheOne 实际在做什么，接下来怎么投入

起因：2026-10-10 的一次审查。审查指出，TheOne 已经在做任务调度、选择工作目录、控制执行，却仍然把自己说成「自动整理聊天」。这份文档逐条核对现状，给出方案，并列出需要你决定的事。**按计划表规则，这里的改动都先不写代码，等你确认。**

优先级（你定的）：**执行资源隔离 → 纠错后的恢复 → 连续真实使用验证**。多平台推迟，等这三项有了明确方案再说。

## 0. 定位和设计语言

**核对结果：审查说得对。** 现在每收到一条消息，TheOne 都会替用户决定四件事：

- 交给哪个话题（也就决定了模型看到什么上下文）；
- 在哪个文件夹干活（新话题有关联项目时自动选那个项目，`src/index.ts` 的 `worker()` 和 `classify()`）；
- 是马上在后台开工，还是排队（回复进行中又来的消息，`sortMidReply` / `startBackground`）；
- 什么时候展示、按什么顺序合并回主聊天。

这些都是执行层面的决定。

计划表的第 4 条设计语言「只整理，不改动」只覆盖了一半。不改用户的会话和设置，这一点仍然成立。但 TheOne 替用户决定了在哪儿动手，而这件事只是「整理」说不清楚。

**建议把第 4 条改写成：** 「不改用户的会话和设置；TheOne 替你决定在哪个话题、哪个文件夹做事，所以这个决定必须让你看得见、一句话改得了。」README 的一句话介绍也相应从「自动整理聊天」改成「替你分派、在对的地方接着做」。

→ **需要你决定：** 是否改写设计语言第 4 条和 README 的定位（措辞可以再改）。

## 1. 执行资源隔离（第一优先）

**现状。**

- 话题之间只隔离了上下文，没有隔离工作资源。
- 同一个项目文件夹里，最多可以有三个话题同时在跑：一个在前台，两个在后台。它们可以同时改同一个文件、切 git 分支、装依赖。
- 后台并发上限（0.3.31 刚修好竞态）只管数量，不管它们是不是落在同一个文件夹里。
- 用户自己在同一文件夹开的普通会话，TheOne 管不到。这一点和原生一致：原生允许两个会话共用一个工作区，但那是用户自己选的。现在的情况是 TheOne 替用户开的并行，所以冲突的责任在 TheOne。

**方案：按文件夹调度写操作。读可以并行，写要排队。**

- **阶段 0（小改动，可以先做）：同一文件夹不在后台并行开工。**
  - 回复进行中来了一条别的事，如果它的话题和正在跑的话题在同一个项目里（按 git 仓库根目录判断，没有 git 就按文件夹判断），就不在后台提前开工，等主聊天轮到它再做。
  - 这本来就是现有的退路（「否则这条消息就等着轮到它」），只是多加一个条件。
  - 代价：同一个项目里纯读、纯问答的事也不并行了。
- **阶段 1：写租约。**
  - 每个项目（git 根目录或文件夹）同时只给一个话题发「写租约」。
  - 话题在第一次调用可能改动东西的工具时申请租约，这次回答结束时归还。可能改动的工具：write、edit、有修改的 str_replace_editor、shell 命令、启动后台任务。read、grep、看图这类只读工具不需要租约。
  - 拿不到租约的话题就在那个工具调用上等着，主聊天的工具卡片上显示一行「等『A』在 proj 里改完」，然后自动继续。
  - 这样读和想可以并行，写变成串行。
  - 不会死锁：每个话题同一时刻只在一个文件夹里申请，而且只申请一次。话题派出的子代理用父话题的租约。
  - 已知不覆盖的部分：
    - 命令里用绝对路径写到别的文件夹；
    - 这一轮启动、结束后还在跑的后台任务（比如开发服务器），租约随回答结束一起还掉，否则会永远占着；
    - 用户自己开的普通会话。
- **阶段 2：worktree 隔离（只在用户同意时用）。**
  - worktree 会在用户的仓库里新建 `.git/worktrees` 条目和分支，改完还要合并回来。这违反「不改用户的东西」，合并的负担也落在用户身上。
  - 建议只作为按项目手动打开的选项，不作为默认。

→ **需要你决定：**

1. 阶段 0 能不能先做？
2. 「读并行、写串行」这个语义对不对？shell 命令一律算写，会不会太保守？
3. worktree 是不做、可选，还是默认？

## 2. 运行状态和纠错后的恢复（第二优先）

### 2a. 统一的生命周期

**现状。**

- 路由记录在 SQLite 里，只有 `planned → running → completed / failed` 四个状态。
- 执行中的状态分散在内存里：`runs`、`background`、`sorting`、`starting`、`relays`；另一部分在 DSH 自己的会话和收件箱里。
- 进程中断后，这几处对不上。

**已经证实的一个后果**（用测试复现过，未修）：

- 一条消息已经在后台话题里开工、主聊天还没轮到它时，DSH 重启了。
- 重启后主聊天轮到这条消息，会直接报英文错误「This input has already started… automatic replay is disabled.」。
- 用户既看不到话题已经做了什么，也没法让它接着做。

**方案：每条消息一条完整记录，重启时按规则对齐。**

- **状态：**
  - 已收到；
  - 已分配（选好了话题和文件夹）；
  - 进行中（细分为等授权、等回答、等写租约）；
  - 完成但还没展示（后台做完了，主聊天还没轮到）；
  - 已展示；
  - 失败；
  - 中断。
- **持久化：** 在路由记录里加三项：话题会话 id 和这一轮的起点、是否已经执行过可能改动东西的工具、是否已经展示。
- **重启时的规则：**
  - 已分配但还没开工：照常做，什么都还没发生，安全。
  - 进行中、还没做过改动：可以自动重做。也可以统一不重做，见下面的待决定。
  - 进行中、已经做过改动：**不自动重做。** 轮到它时，主聊天用用户的语言说一句：「这件事在 DSH 重启时做到一半：已经在 proj 改了 readme.txt、运行了 3 条命令。说『继续』就接着做。」改动的内容从话题会话里读，DSH 会话里的工具调用是持久保存的。用户说「继续」后，话题收到「上次做到一半被中断，先检查现状再接着做」。
  - 完成但还没展示：直接把话题已有的回复展示到主聊天，不重做。
  - 中断时正在等授权或等回答：DSH 重启后这些弹窗就没了，按「已经做过改动 / 没做过」走上面两条。

### 2b. 「分错了」之后的完整闭环

**现状**（`applyCorrection`、`correctedInput`）：

- 纠正会把原消息交给正确的话题重做，并调整两个话题的学习词。
- 但错误的话题已经收下了这条消息和它的回复。它们留在错误话题的上下文里，会影响它以后的回答；它的摘要卡片和事实提取（默认关闭）也会照常把这一轮算进去。
- 如果那一轮改了文件或执行了命令，这些改动还在，主聊天里也没有提示。

**方案：纠正之后，分清哪些影响已经修复、哪些交给用户处理。**

- **记下错误的那一轮：** 记录话题、会话和这一轮的范围。
- **TheOne 能修复的：**
  - 错误话题的摘要卡片、相关历史搜索、事实提取和给其他话题的简报，都跳过这一轮；
  - 错误话题下一次开工时，收到一句提示：「第 N 轮那条消息不属于这里，已经转给『X』，不要沿用」。DSH 的会话只能追加，删不掉那一轮，只能这样抵消。
- **交给用户的：**
  - 纠正后的回复开头列出那一轮已经造成的影响：改了哪些文件（带改动卡片，可以点开看对比）、运行了哪些命令、还有哪些子代理或后台任务在跑（可以直接停）。
  - **不自动撤销**：撤销可能覆盖用户之后的修改。
- **以后可以考虑：** 只在 git 项目里、而且文件在那之后没再被改过时，提供「撤销那一轮的改动」。

→ **需要你决定：**

1. 中断时还没做过改动的任务，是自动重做，还是统一等用户说「继续」？我倾向统一等，行为更好预期。
2. 「撤销那一轮的改动」要不要做？

## 3. 连续真实使用验证（第三优先）

**现状。**

- README 公布的 91.6% 和 86.6% 来自合成的开发集，只测「消息分到哪个话题」。
- 测试数据里没有助手的回复；真实使用中最难的模糊消息被排除在严格评分之外（`eval/README.md`）。
- 它说明路由准不准，不能说明用户是不是少操心了。

**方案：先选一类用户、一种连续使用场景，和原生多会话对比。**

- **用户：** 同时推进 2–3 个代码项目、中间夹杂日常提问的开发者，每天用 DSH 一小时以上。
- **做法：** 两周，原生多会话和 TheOne 隔天交替使用，同一个人做同类事情。
- **指标**（都在本机记录，只记次数和时间，不记内容，需要用户主动打开）：
  - 找回旧事：从提到旧事到在正确上下文里得到回答的时间。原生下记手动切会话、搜索的次数，TheOne 下记纠正的次数。
  - 重复说明：用户重新交代背景的次数。由用户自己的模型在本机判断。
  - 纠错成本：发现分错用了多久，纠正花了几步。
  - 等待：路由多出来的延迟（p50 / p90），路由回执里已经有时间可以用。
  - 每天一个主观问题：「今天有没有因为 TheOne 多操心？」
- **在这之前可以先做的：** README 里写清楚现有评测的边界（合成数据、只测分配准确率、排除了模糊消息），不让公开数字承诺超出它能证明的范围。

→ **需要你决定：**

1. 用户类型和场景选得对不对？
2. 谁来用？只有你自己，还是要找几个用户？
3. README 的说明现在就改吗？

## 4. 之后要做的（排在前三项之后）

- **让用户看得见执行对象。**
  - 主聊天的回复上方加一行「→ 话题 · 文件夹」。只在话题或文件夹和上一轮不同时出现，或者在默认工作区以外写文件时出现，平时不打扰。
  - 支持一句话固定归属：「接下来都是 proj 的事」，在用户改口之前，路由优先放进这个话题。
  - 这条依赖第 1 项（知道哪些操作是写），所以放在后面。
- **话题的粒度和生命周期。**
  - 区分三种：长期事项、具体任务、临时问答。
  - 临时问答不建持久话题，在一个不进目录的地方答完，过一段时间自动清掉。
  - 具体任务做完就休眠：不进路由候选，但能搜到，再提到时重新打开。
  - `docs/proposals.md` 第 2 项「拆分话题」要建立在这套语义上，所以先定这个，再定拆分。
- **宿主适配层和发布门槛。**
  - 现在 TheOne 在 9 处包装了 DSH 的服务：文件、终端、改动、后台任务、问题、会话控制、连接、工作区。另外还有计划模式、命令、压缩等按会话取用的服务，以及 18 处 `as unknown as` 类型转换。每一处都依赖一个 DSH 没有写明的约定。
  - 做法：把这些集中到一个适配模块里，附一张能力清单，写明每项依赖 DSH 的哪个方法、什么约定、由哪个测试覆盖。
  - 把 `e2e/README.md` 里关键的几项完整宿主检查（改动卡片、后台任务、授权、计划模式、重启）做成 CI 任务：在 CI 里装真实的 DSH，配合测试模型和 Playwright。这个任务通过才允许发布。
  - 这件事不改用户可见的行为，可以和第 1 项并行做。我建议在继续补原生能力之前先做。

## 5. 多平台

推迟。等第 1–3 项有了确认的方案，并且适配层已经集中之后再评估（`docs/portal.md`）。
