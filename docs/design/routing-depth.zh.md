# 路由深化：更省、更快、错了也不疼（方案，2026-10-31）

功能先不加了，把底层路由做深。三个维度：**速度**、**准确率**、**省了多少 token**。另外一条原则：剩下那 4% 不一定要分对，但要让用户感觉不到。

这份文档是方案，还没有写代码。里面的数字分两种：评测里实际测过的（会注明来源），和按价格估算的（会写「估算」）。每一步都有上线门槛，过不了就不上。

## 先说结论

1. **最大的省钱点不在本地模型，而在缓存。** 现在每条消息约 1661 个输入 token，只有 37% 命中 DeepSeek 的前缀缓存，因为路由输入的 JSON 第一项就是本轮消息，后面整段话题目录每次都算新内容。把不变的放前面、会变的放后面，估算路由花费能降三到五成，准确率理论上不受影响（要复测确认）。
2. **本地规则能直接定下的消息大约 15%。** 我在 InterleaveBench 上做了一个不调用任何模型的打分实验（见下文 A3）：开发集和测试集都是覆盖约 15%、这部分分对 98.3–98.5%。能省一些，也能让这部分消息几乎零延迟，但撑不起「大部分消息不用 LLM」。原因是评测里 66% 的消息在接着当前话题，而且很多是「场地呢」「那接下来要准备啥」这种只靠上下文才懂的短句，词面上没有线索。
3. **本地打分更值钱的用法是当「第二个裁判」。** 它和 LLM 意见一致时基本不会错；不一致时，才让 LLM 开思考再看一次。现在「放错到别的话题」的错误（2.8%）几乎都来自没触发复核的快速判断，这是补这个洞最便宜的办法。
4. **剩下的错误按伤害分层处理，不是一律去追准确率。** 无害的（一次性算术题放进了相关话题）不管；拆成两个话题的，靠后台合并；真正有害的（一件事的内容进了另一件事），靠「暂定提交」和「从下一句话自动看出分错了」，让它在用户察觉前就被挪走。
5. **「省了多少 token」要做成一本账给用户看**：路由花了多少、多少消息没调用模型，以及话题会话比一个大会话少读了多少（估算，标明是估算）。

## 现在的路由怎么走

按顺序，前一步定了就不走后面：

| 步骤 | 做什么 | 调模型吗 |
|---|---|---|
| 规则快路 | 「分错了」、目标轮次、「好的 / 继续」、回答中途插话、只发图片 | 不调 |
| 候选筛选 | 话题超过 16 个时，按词面、最近使用、关联、DSH 全文搜索挑 16 个 | 不调 |
| 快速判断 | 关思考，选已有话题 / 新建 / 追问 | 1 次 |
| 再判断一次 | 快速判断要新建、追问，或和「只有一个话题提过的数字/编号/名字」冲突时，开思考再问 | 约 18% 的消息多 1 次 |
| 新建前翻目录 | 要新建时，把没进候选的话题分页再问一遍 | 话题多时才有 |
| 收尾 | 拿不准不问用户，落到最可能的话题，主聊天提示「也可能是…」 | 不调 |

另有三道兜底已经在插件里：话题自己发现不是它的事会退回（`theone_handback`），第一次动手前会核对对象，用户说「分错了」会把那一轮从错的话题里抹掉。后两者都没进评测，因为评测数据还没有助手回复。

## 三个维度怎么量

先把尺子做好，否则后面每一步都说不清好坏。评测脚本（`eval/run-router.mjs`、`eval/score.py`）加这些指标：

| 维度 | 指标 | 现在有没有 |
|---|---|---|
| 准确率 | 分对比例、放错到别的话题、一件事拆成几个话题、无谓追问 | 有 |
| 伤害 | 按 `score.py` 里已有的代价表（放错 3、合并进新话题 3、多拆 1）算每百条消息的代价 | 有代价表，没在 README 里报 |
| 速度 | 每条消息的模型调用次数；延迟中位数和 90 分位（本地定下的算 0） | 有总延迟，没分层 |
| token | 每条消息输入 / 输出 token、缓存命中率、每千条花费；按「本地 / 快速判断 / 再判断 / 翻目录 / 卡片」分开记 | 有总数，没分层 |
| 无感 | 「被察觉的错误」：分错之后，到下一条消息结束时还没被自动挪走的比例 | 没有，C 部分要用 |

插件里每条路由已经有一张回执（`RouterReceipt`：模式、模型、耗时、token）。加上「哪一层定的」和缓存命中数，账本（D 部分）就有数据了。

## A. 省 token、提速：先做不碰判断逻辑的

### A1. 路由输入改成「不变的在前」

现在 `routingPayload` 输出的顺序是 `text → contexts → currentId → recent → …`。DeepSeek 的缓存按前缀逐段匹配，第一项就变了，后面全部算新。改成：

1. 话题目录里不常变的部分：id、标题、简介、名字、关键词。顺序按话题 id 固定，不按本轮候选得分排（候选筛选只决定放哪些，不决定顺序）。
2. 常变的部分单独一块：每个话题的「当前状态」、最近活跃时间、status（当前话题回复一次就会变）。
3. 近期消息 `recent`。
4. 纠正样例、要点、正在进行的回复等可选项。
5. 本轮消息 `text` 放最后。

系统提示词里按条件追加的几段（要点、项目、进行中、复核）也挪到用户消息里，让系统提示词每次完全一样。

估算（按 V4.1 Flash 价格，开发集 open 模式的 token 量）：命中率从 37% 到 65%，快速判断每千条 $0.41 → 约 $0.27；到 80% 约 $0.20。实际能到多少，取决于目录和近期消息各占多少，要在评测里实测。缓存命中的请求首字也更快。

门槛：准确率、放错比例和改之前比，配对抽样的区间包含 0（不变差）；命中率和花费按实测写进 `docs/routing-eval.md`。

### A2. 早提交：知道去哪就开工

模型输出的 JSON 里 `action`、`contextId` 在前，`reason`（最多 120 字）在后。现在要等整段输出完才开始干活。改成流式解析：已有话题的判断一读到 `contextId`，就让那个话题开工，`reason` 和 `relatedIds` 读完再补上（参考资料晚一点到，话题第一步之前能补上就带上）。同时把 `reason` 限到 40 字左右。

评测里快速判断的输出约 73 个 token，大部分是 `reason`。省下的是这部分的生成时间，估计每条消息快不到 1 秒，具体按评测里记录的首字时间和总时间算。

门槛：准确率不变（`reason` 变短可能影响判断，要测）；延迟中位数下降。

### A3. 本地快判：有把握的不调模型

对每个已有话题，用它收到过的消息算一个词面得分（字两两切分 + 英文单词，按「几个话题都有」降权，和现在候选筛选用的 `textFeatures` 同一套）。两条规则：

- **留在当前话题**：当前话题的得分比别的话题都高出一截，而且「只有一个话题提过」的数字/编号/名字没有指向别处。
- **切到另一个话题**：某个话题的得分比当前和其他话题都高出一大截，线索也不反对。

其余消息照常交给 LLM。

**实验（2026-10-31，脚本在会话临时目录，没进仓库）**：在 InterleaveBench 上逐条重放，事先给好话题列表，用真实标签代替「已经确认的路由历史」（偏乐观：实际使用时历史里会有分错的）。门槛在开发集上挑，在测试集上看：

| 规则 | 开发集覆盖 | 开发集分对 | 测试集覆盖 | 测试集分对 |
|---|---|---|---|---|
| 只「留在当前」（领先 ≥3） | 9.7% | 98.8% | 11.6% | 98.0% |
| 只「切到别处」（领先 ≥6） | 4.1% | 97.1% | 4.5% | 100% |
| 两条合起来 | **13.8%** | **98.3%** | **16.1%** | **98.5%** |
| 对照：只认「只有一个话题提过」的线索 | 10.3% | 85.3% | 10.4% | 84.1% |

（`continuesCurrent` 那条「好的 / 继续」快路在评测里覆盖 0%，因为评测数据没有这类句子；真实使用中它本来就省掉一部分调用。）

开发集错的 4 条里，2 条是「帮我算一下 9860 加 6800」这种一次性算术题被放进了提过这些数字的话题，危害很小；另外两条是真错（「对了那个蛋糕…」回到旧话题，被留在了当前话题）。

这一步的收益：约 15% 的消息不调模型、几乎零延迟，路由花费再降一成多。要上线，还要用插件自己的整条流程重放（open 模式、带卡片），确认总准确率和放错比例不变差。门槛定得保守：本地定下的那部分要不低于 LLM 在同一批消息上的准确率。

注意：一次性算术、换算这类问题要先排除（规则判断「纯计算」就交给 LLM），否则数字线索会把它们拉进相关话题。

## B. 本地当第二个裁判：减少有害的错

### B1. 意见不一致才复核

现在只有「新建、追问、和唯一线索冲突」才开思考再看一次。评测记录里，放错到别的话题的错误主要来自没触发复核的快速判断（留在当前话题 24 例、切到另一个话题 18 例）。

把 A3 的本地打分也当成一个裁判：LLM 选了 X，本地明确倾向 Y（得分领先过线），就触发复核。两边一致就不复核。这样复核比例只会小幅上升（B1 实验要测出具体比例），专门抓「快速判断自信地选错」这一类。

实验：在现有评测里记下每条消息本地的倾向，离线统计「本地和 LLM 不一致」时 LLM 错的比例。如果不一致的消息里 LLM 错得明显多（比如三成以上），这个触发条件就值得上；再跑整条流程看放错比例能降多少、复核比例涨多少。

### B2. 不挡路的复核

复核要多等一次开思考的调用（评测里合计约 12 秒）。对「有一点分歧、但没到复核线」的消息，可以先按快速判断开工，同时在后台复核：

- 复核同意：什么都不发生。
- 复核反对，而且话题还没动手（没改文件、没跑命令，只在写回答）：停下这一轮，挪到复核选的话题重做，主聊天显示「已换到「B」」。错的那一轮按「分错了」的规则抹掉。
- 复核反对，但话题已经动手：不自动挪，回答末尾提示「这条也可能是「B」的」，用户说一句「分错了」就挪。

代价是复核推翻时，第一个话题已经写的那部分白费。要统计推翻的比例，估算浪费的 token，和省下的等待时间一起比较。这一步改动大，放在 A、B1 之后。

## C. 剩下的错误：让它不疼

### 先把错误分层

| 类型 | 例子 | 伤害 | 处理 |
|---|---|---|---|
| 无害 | 「22 篇离 30 篇还差几篇」进了开题报告的话题 | 很小 | 不处理 |
| 多拆一个话题 | 同一件事被开成两个话题 | 中：上下文分散 | 已有的合并建议；C3 |
| 放错到别的话题 | 读书会的预算进了求职的话题 | 大：两件事的上下文互相污染 | C1、C2、话题退回 |
| 动手动错了地方 | 在错的项目文件夹里改文件 | 最大 | 已有「动手前核对」 |

目标不是把准确率从 96% 推到 99%，而是让「放错到别的话题」在用户察觉前被挪走，把「被察觉的错误」压下去。

### C1. 暂定提交：确认之前不学

现在一条消息路由之后，马上影响这些东西：话题卡片的重写、话题之间的关联、从纠正里学的词、要点（已定的数值）。如果这条是分错的，错的东西已经学进去了，后面的路由会跟着错。

改成：一轮回复先算「暂定」，下一条用户消息没有表示分错（没有「分错了」，C2 也没看出问题）才转成「确认」。卡片重写、关联学习、要点只吃确认过的轮次。用户隔了很久才发下一条，就在一段时间后自动确认。

这不改路由本身，改的是「错一次之后不要越错越多」。

### C2. 从下一句话看出分错了

用户发现分错时，大多不会说「分错了」，而是换个说法再问一次，或者补一句「我说的是读书会那个」。对话系统研究里，「换个说法重问」一直被当作用户不满意的信号（Sano 等 2017；arXiv 2010.12251 列了打断、放弃、「不是……」开头、重新表述等几类）。

本地检测（不调模型）：

- 新消息和上一条用户消息很像（词面相似度过线），而且多了一个只属于另一个话题的名字、数字或标题词；
- 新消息以「不是」「我说的是」「我问的是」「另一个」开头，后面点到了别的话题；
- 新消息被路由到 B，而上一条在 A，两条又很像。

命中时，把「上一条可能也属于 B」交给 LLM 确认一次；确认就按「分错了」的流程把上一条挪到 B（错的那一轮抹掉、改动列出来），主聊天一句话说明。用户什么都不用做。

评测：现有数据里有大量「切换」和「回到旧话题」的消息，可以造一个变体，在分错的地方插入一句模型生成的「换个说法重问」，看能自动挪回多少、误挪多少。误挪必须很低，否则比不做更糟。

### C3. 话题自己退回，进评测

`theone_handback` 已经有了：话题发现消息明显不是自己的事，在写任何东西之前退回，重新路由。但现在没有数据说它多久触发一次、对不对。评测 v1（带助手回复的那版）加一组：故意把一部分消息送错话题，看话题能退回多少、误退多少。数字好，就把它当成「快速判断之后的第三个裁判」写进 README；数字差，就改它的提示词。

### C4. 拿不准时，回答第一句点明按哪件事理解

只在路由犹豫（有 `alternateIds`）时，让话题回答开头用半句话点明「按读书会那边的预算来说」。用户一眼就知道它理解成了哪件事，错了马上能说。不犹豫时不加，避免啰嗦。这是文案和提示词的事，最后做，先看 C1、C2 的效果。

## D. 「省了多少 token」做成一本账

两件不同的事，分开记、分开说：

1. **路由本身花了多少**（实打实的数）：每条消息哪一层定的、调了几次模型、输入输出 token、缓存命中；按天汇总。「本地定下」「规则定下」的条数就是省下的调用。
2. **话题会话比一个大会话少读了多少**（估算）：TheOne 的核心好处是每件事的上下文小。每个话题回合实际送给模型的输入 token 是 DSH 记录的；对照值是「如果所有事都在一个会话里，这一轮要读多少」，用主聊天全部历史的长度估算，按同一个模型的上下文上限和压缩阈值截断。两者之差累加，界面上写明「估算」。

放在话题工作区底部，一行就够：「本月路由 N 条，其中 X% 没调用模型，花费约 $Y；话题会话比单个会话少读约 Z 万 token（估算）」。设置里能展开看按层的明细。数字只存在本机，反馈里只带汇总值。

## E. 本地 embedding 模型：先离线验证，过线再说

GitHub 上常见的做法是用小的向量模型做路由（aurelio-labs/semantic-router 用本地编码器，按每个路由调阈值）。能用在 Node 里、又不需要本地编译的选择：

| 模型 | 体积（量化后） | 中文 | 在 DSH 插件里怎么跑 |
|---|---|---|---|
| potion-multilingual-128M（model2vec，bge-m3 蒸馏的静态向量） | int8 约百 MB 量级 | 支持 | 只是查表求平均，可以纯 JS 实现，不需要推理引擎 |
| multilingual-e5-small | q8 约百 MB 量级 | 支持 | transformers.js + onnxruntime-web（WASM，`--ignore-scripts` 安装也能用） |
| bge-small-zh | 类似 | 只中文 | 同上 |

我的判断是先不进插件，原因：

- 体积。插件现在只有一个运行时依赖，下载一个百 MB 级模型对国内用户还要走镜像（HF 不通，要 hf-mirror 或 ModelScope），只能做成可选。
- 收益不确定。A3 的实验说明，评测里难分的是「场地呢」这种靠上下文的短句，向量模型对它们帮助有限；它更擅长「换了说法但讲的是同一件事」。

所以只做离线实验：用 Python 在 InterleaveBench 上算这几个模型的向量，替换 A3 里的词面得分，看「分对不低于 98.5%」时覆盖能从 15% 涨到多少。涨到 35% 以上，再考虑做成可选的「本地加速包」；涨不了多少，就记一笔「试过、没用」写进 `docs/routing-eval.md`。

## 不做的

- **多模型选择**（RouteLLM 那类在强弱模型之间选）：TheOne 用的就是用户在 DSH 里选的模型，路由层不该再替用户挑模型。路由和干活用不同模型，已经可以在模型按钮旁的图层图标里设。
- **多次投票**：30 RPM 的限速下太慢。
- **按 logprob 判断把握**：DSH 的接口拿不到。
- **SQLite 中文分词扩展**（wangfenjin/simple）：要分发原生二进制，和插件「不用编译、`--ignore-scripts` 能装」的做法冲突；现在两两切字的办法已经够用。

## 顺序和门槛

每一步都在 InterleaveBench 上跑开发集和测试集，和上一版做配对比较。准确率和放错比例的变化区间不能明显偏向变差。

| 阶段 | 内容 | 门槛 | 大致工作量 |
|---|---|---|---|
| 1 | 尺子：分层记录调用、token、缓存、延迟，score.py 报伤害代价；A1 缓存重排；A2 早提交 | 准确率不变差；花费、延迟实测下降 | 一周内 |
| 2 | A3 本地快判 + B1 第二裁判（先离线统计，再整条流程重放） | 本地定下的部分不低于 LLM；放错比例下降 | 一周 |
| 3 | C1 暂定提交；C2 从下一句看出分错（先造评测变体） | 误挪很低；「被察觉的错误」下降 | 一到两周 |
| 4 | D 账本界面；C3 进评测 v1；E 离线实验 | 看实验结果决定 | 穿插 |
