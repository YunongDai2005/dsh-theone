# 路由调用的缓存优化：24 个方向与最小实验

日期：2026-11-03。源码观察点：routing-depth 分支，5aab4df。本文是设计研究，不是实现或实测性能报告。

优先试三件事：**把会变的目录改成版本化快照加覆盖层；缩小路由输出协议；按完整状态复用相同判定并合并重复在途请求。** 三者分别减少未命中输入、生成 token 和重复调用，能独立验证，也能组合。只追加的路由长会话值得做对照实验，但应限制长度；不建议为了 99% 命中率保留无限历史。

任务给出的约 2,900 输入 token、130 输出 token、1.1 次调用/消息、77% 服务端命中率，是本文的情景基线，并非本轮重新测得。除特别注明的源码核对与离线计算，所有收益数字都是带条件的估算；不能相加当作已经实现的收益。

本轮只新增本文，不改代码、不读取凭据、不调用模型 API。任务文件写了“不要 commit”，本轮用户消息又明确要求“验证、提交”，按最新直接指令，仅尝试本地提交本文；结果以最终 Git 汇报为准。

### 服务端规则中最容易误用的地方

官方文档描述：缓存按完整前缀单元匹配，输入/输出结束处、重复请求的公共部分、长序列的间隔处可形成单元；缓存异步构建且尽力保留。例子中“第三次才命中”特指 A+B、A+C、A+D 的公共部分发现过程；A+B 后继续 A+B+C 可以复用已有单元，不能一概认为必须先发两次预热。[DeepSeek 缓存规则](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)

这里的工程目标是保持**模型看到的角色、内容、分隔和 token 前缀**稳定。“字节稳定”是有用的客户端约束，HTTP 外层 JSON 属性顺序本身却不等于模型 token 顺序。请求头里的追踪 ID、本地 sessionId 也不能未经验证就当作破坏缓存的原因。把相同摘要放在不同前文之后，不会因此得到可独立拼接的官方 KV 缓存。

当前文档没有给出可依赖的固定间隔数值，不应把旧工具里的 64 当成新模型保证；拆成两条 user 消息，也不等于能命令服务端立刻落盘。[同一官方规则](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)

对于当前使用的 Chat Completions 路线，多轮仍要发送历史；客户端留着一个“会话 ID”并不会自动免掉历史输入费用。[DeepSeek 多轮对话](https://api-docs.deepseek.com/zh-cn/guides/multi_round_chat/) 缓存也不是复用上次的判定结果，新的输出仍要生成。

## 2. 用什么指标判断值得做

### 主指标与成本模型

主指标应是**每条用户消息的全部路由成本、未命中输入 token、调用数和可见等待时间**；服务端命中率作为解释指标。

~~~text
H = 所有实际请求的缓存命中输入 token 总数
M = 所有实际请求的缓存未命中输入 token 总数
O = 所有实际请求的输出 token 总数
命中率 h = H / (H + M)
成本 C = p_hit × H + p_miss × M + p_out × O
~~~

不要平均每次调用的百分比。快路、结果缓存的零调用不要伪造 100% 服务端命中；usage 缺失应标为未知，不能记作全未命中或零费用。路由、复核、翻页、卡片、预热、失败/重试、投机请求分别列账，再合计。旧离线回答缓存里的历史 usage 不能当成本轮实际消耗。

为让方案可比较，设每调用输入 P、输出 Q、每消息调用 c，r=p_hit/p_miss，s=p_out/p_miss：

~~~text
V = c × [ P × (1 - h + r × h) + s × Q ]
~~~

V 是按未命中输入单价折算的成本单位，不是实际 token 数。真实核算仍需逐次累加，不能用三个均值替代调用间相关性。

2026-11-03 查阅的官方 Flash 价目：缓存命中/未命中/输出，高峰每百万 token 为 0.04/2/8 元，空闲为 0.02/1/4 元，因此 r=0.02、s=4；官方名称 deepseek-flash 对应 V4.1-Flash-1017。任务中的“V4.1 Flash”按同一模型家族理解，没有修改任何配置。[官方价目](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)

**这个价格只用于下面的直连官方 API 情景。** 当前仓库已有报告提到 OpenCode Go；兼容接口、套餐和转售商可能采用别的计费与缓存规则。本文没有连接实际账号、验证实际端点或读取账单，不能把情景金额当作用户支出；复核的思考 token 也可能使真实平均输出超过任务给出的 130。

### 同一基线下的量级

代入 c=1.1、P=2900、Q=130、h=0.77：

- 每调用未命中输入 667；每消息未命中输入约 733.7，输出约 143。
- V=1354.826；官方高峰情景约 2.709652 元/千条消息，空闲减半；不含另外产生的卡片等请求。
- 即使只优化输入，输出项也占这份情景账单约 42.2%，所以输出协议值得单独优化。

| 只改变表内因素，其他不变 | V / 消息 | 相对基线节省 |
|---|---:|---:|
| 基线 | 1354.826 | — |
| 命中率 85% | 1104.730 | 18.46% |
| 命中率 90% | 948.420 | 30.00% |
| 命中率 95% | 792.110 | 41.53% |
| 输出 130 → 60 | 1046.826 | 22.73% |
| 输出 130 → 30 | 914.826 | 32.48% |
| 调用 1.1 → 1.0 | 1231.660 | 9.09% |
| 均匀省掉 20% 同分布请求 | 1083.861 | 20.00% |

这些是单因素敏感性分析，不是方案预测，尤其不能把最后一行解读成“本地规则已经能覆盖 20%”。只省最便宜的 KEEP，或剩下的请求更难、复核更多，节省会小于按消息覆盖率推算的值。

若每次必须新增且不可复用的输入为 U，固定输入规模 P 下的理想命中上界约为 1-U/P。例如 U=200 时约 93.1%，U=400 时约 86.2%。在 2900-token 输入上追求 99%，相当于只留下约 29 个未命中 token；通常不能靠重排充分表达的新消息实现。

## 3. 请求组织与缓存结构

下文的难度按“低：序列化或局部流程；中：版本、状态或协议变化；高：新分类器、日志系统或推理基础设施”估计，不是工期承诺。所有最小实验都是建议；本轮只执行第 8 节列出的离线检查。

### 01. 固定模板版本，稳定可选能力的说明

- **思路：** 按协议、语言、已启用能力形成少量模板版本；选定版本后，不因单次 attention/running 是否为空改前部。请求时钟、活跃度、人类可读状态放尾部。对模板和稳定区分别记录哈希。
- **收益机制/估算：** 修掉模板切换造成的早期分叉；仅当确有分叉流量时获益。假设能把 100 个输入 token 从 miss 变为 hit，每调用减少约 98 个成本单位；不要增加数百 token 的永久说明来消除很少出现的切换。
- **准确率/延迟风险：** 把所有说明固定拼上可能增加输入、冲淡主任务；换模板有冷启动。不能删除 attention 语义来换稳定性。
- **实现难度：** 低；当前已有大部分固定说明，增量主要是 attention 变体及版本治理。
- **最小实验：** 人工构造有/无 foreground、pending、running 的请求，比较前缀位置和等价路由语义；以后只对实际常见的两三个模板变体做命中对照。

### 02. 版本化目录快照，加最新覆盖层

- **思路：** 将目录拆成一个 epoch 内不可变的基础快照，以及尾部最新的 add/update/delete 覆盖层；同一 id 以最高 revision 为准。新话题、纠正、卡片和状态立即进覆盖层，积累到阈值后才重建快照。固定候选池加溢出候选，避免每次完全重写 contexts。
- **收益机制/估算：** 最早变化从某个目录项内部移到快照之后。假设 2900-token 请求中可多复用 300/500 token，h 分别可增加约 10.3/17.2 个百分点；额外覆盖层也要计入 P，不能只报百分比。
- **准确率/延迟风险：** 旧摘要与新修订可能冲突；删除/合并映射、纠正和项目边界必须确定覆盖优先级。固定池也可能漏新话题，须保留本地检索的溢出入口和原有 review。
- **实现难度：** 中；关键是原始状态到“快照+覆盖层”的语义等价，不是简单缓存 JSON。
- **最小实验：** 先用 20 条人工 add/update/delete/merge/correction 事件，证明物化后的有效目录与直接序列化一致；再比较冻结 4/8/16 条消息的候选池与原始池的召回和字节增长。第一轮先不改候选选择，只冻结描述并传完整最新覆盖，隔离变量。

### 03. 按变化概率组织前缀，而非按相关性排序

- **思路：** 在 epoch 开始时把不常变的卡片放前面，近期频繁更新的卡片靠后；动态 activity 继续在尾部。输出 id 不随位置重编号。epoch 内不按最新访问时间反复重排。
- **收益机制/估算：** 两段长度为 L_A、L_B、变化概率 q_A、q_B，假设独立时，A 在前更有利的条件是 q_B×L_A ≥ q_A×L_B；即优先考虑 L/q 较大者，而非简单“最常用在最前”。长且稳定的片段更能保护后方。
- **准确率/延迟风险：** 模型有位置偏好；最相关信息后移可能伤召回。变化概率估计过拟合，频繁重排反而清掉收益。
- **实现难度：** 低至中；必须与候选选择分开，并保持编号映射。
- **最小实验：** 在相同候选、相同内容的脱敏序列上，比较现有目录序、创建序、按历史变化概率排序；只做一次冻结排序，记录首变位置，不宣称理想前缀就是实际命中。

### 04. 固定项目/候选簇，减少“子集抖动”

- **思路：** 由本地项目、显式回复绑定或高置信检索选择少数稳定的候选簇，每簇维护自己的快照；跨项目和不明确请求进入全局通道。允许双簇参考，不强行把每条消息锁在一个项目。
- **收益机制/估算：** 候选成员不再每轮都变，簇内缓存可以复用；但流量被拆小后更容易冷。对簇 j，比较其 N_j 条请求中的新增冷成本与恢复的缓存成本；没有访问频率数据就不给命中率承诺。
- **准确率/延迟风险：** 同项目多任务不能混为一题；当前项目也不一定是目标。簇选错会造成候选级漏召回，而后级模型无法弥补。
- **实现难度：** 中。
- **最小实验：** 用同项目两件事、跨项目同名事项和跨话题对比的人工序列，验证溢出召回；离线统计每簇生命周期和请求数，先淘汰只有一两次访问的分簇策略。

### 05. 把多次路由做成有界、只追加的长会话

- **思路：** 以一份目录快照起步，每轮只追加本轮事件和用户输入，保存模型实际返回的 assistant 路由结果；下一轮逐字保留已有 message 内容、角色和边界。修订以新事件追加，不能重写旧消息。原始输出与业务归一化结果分别保存。
- **收益机制/估算：** 上一轮的整个输入/输出结束前缀可成为下一轮复用单元，新计算主要是尾部增量；不再让滑动 recent 和目录改写切断历史。有限轮次下可能明显降低 M；详见第 5 节，不等于总费用必然降低。
- **准确率/延迟风险：** 历史错路由会强化后续误判，修订语义和长上下文干扰会累积。高命中也仍有历史读入、传输、排队和生成成本；多网关同时写日志会产生乱序。
- **实现难度：** 高；需串行提交、revision、分支、恢复和淘汰机制。先只做 quick 通道，复核用分叉，不能把晚到结果写回更早状态。
- **最小实验：** 同一序列比较现有单轮、快照覆盖层、8/16/32 轮日志；包含纠正、话题删除/合并、崩溃恢复、前台切换和历史过期。原样保留 assistant 内容，另做“重序列化旧输出”的负对照，服务端探针留待另行授权。

### 06. 依成本自适应换代，而非无限增长或固定滑窗

- **思路：** 对方案 05，在历史长度、覆盖事件数或风险达到阈值时建立新 epoch；新快照由本地有效状态生成，避免为了压缩再调用模型。先不删除旧 epoch 的前几条然后继续冒充同一前缀。
- **收益机制/估算：** 换代付一次冷启动，换来后面每次少付历史缓存读费。若旧历史能少读 L token、预计继续 K 次，收益约 K×r×L；与新快照的额外冷成本比较，选择更便宜者。
- **准确率/延迟风险：** 换代时遗漏纠正或前台/待答关系会让语义回退；估计未来 K 不准会过早换代。需要保留独立可恢复的业务真状态。
- **实现难度：** 中至高，依赖 05；新 epoch 会形成新缓存分布。
- **最小实验：** 扫描 8/16/24/32/64 轮及累计字节阈值，统一计入换代首请求；比较全流平均成本、p95 延迟和纠正后的恢复，不只看最后一条命中率。

### 07. 初判/复核共享主干，卡片另建分支

- **思路：** quick 与 recheck 尽量共享不变系统和目录前缀，只把疑点和初判放尾部；翻目录各页共享其共同主干。卡片的任务和内容不同，使用独立模板或话题分支，不把卡片输出混进路由主日志。
- **收益机制/估算：** 当前 quick/recheck 已有相同固定说明，新增收益要来自稳定主干和分支复用。若每消息有 0.1 次附加调用，每次额外恢复 2000-token 命中，理论少付约 0.1×2000×0.98=196 单位/消息；真实分支和思考模式是否共享须验证。
- **准确率/延迟风险：** 复核若直接承接初判文本会有锚定偏差；卡片的安全边界与路由指令不同，强行统一会增加提示词污染。
- **实现难度：** 中；改变 thinking 参数不能擅自视为必然可共享 KV。
- **最小实验：** 以相同任务和疑点分别构造共享主干/独立模板对照，先离线确认前缀；未来只测实际端点返回的 usage，不依据参数相近就报节省。

### 08. 显式“种”公共前缀、预热与保活

- **思路：** 在已知即将有一簇真实请求时提前发送相同主干，或让前两个真实请求自然种出公共前缀。纯预热只用于把冷延迟移出用户等待窗口，不默认定时保活。
- **收益机制/估算：** 设 W 为预热总成本，K 为真正受益的冷请求数，每条减少 miss 的量为 D，则净收益是 K×D×(1-r)-W。S=2400、只输出 1 token 的全冷种子约花 2404 单位；只避免一次同长冷输入最多省 2352，尚未算第二个种子和过期，净成本已经不划算。
- **准确率/延迟风险：** 无直接语义收益；缓存异步完成，预热后立刻发也可能没命中。纯保活增加请求、队列和账单；切分角色边界不当可能完全没有种到预期单元。
- **实现难度：** 低至中。
- **最小实验：** 先用公式筛掉负净收益；未来对“无种子、一个种子、两个种子”分别做 0/2/5 秒间隔探针，计入所有请求。不把预热请求藏在命中率分母外。

### 09. 用真实工作自然建立前缀，按小时间预算调度

- **思路：** 优先复用真正需要的请求；同一快照的一组后台卡片或评测请求靠近调度，避免毫秒级同时到达而共同冷启动。交互消息不为命中率等待几秒。
- **收益机制/估算：** 若同簇请求落在缓存构建之后，可能恢复一部分重复冷 miss；等待成本则直接加到用户延迟。可尝试后台任务短暂合并，交互路径从 0 额外等待起步。
- **准确率/延迟风险：** 重排有因果关系的用户消息会用错状态；串行等待可能使 p95 变差，也不能保证服务端节点亲和。
- **实现难度：** 中。
- **最小实验：** 仅模拟互不依赖的后台队列，比较立即并发、有限并发、按快照分组；记录墙钟耗时和峰值并发。真实流量不改变消息先后顺序。

## 4. 直接少调用、少输出，以及不同架构

### 10. 严格证据本地快路，新增覆盖只计增量

- **思路：** 在现有绑定与续接规则之外，仅对唯一、可验证的引用目标放行，例如明确的消息回复身份、唯一待答关系、用户纠正映射；冲突、弱关键词、否定和新任务转向照常走模型。
- **收益机制/估算：** 本地判定消除整次请求，包括输出和网络等待；新增覆盖率 f 的省费取决于所省请求的原始成本。假设剩余请求完全同分布，新增 10% 覆盖才近似省 10%，不是总快路比例。
- **准确率/延迟风险：** 错误 KEEP 会静默混入另一任务，代价高于很多 CREATE；“继续”已有前台规则，不能另写更粗的正则覆盖它。后台新通知也不能替代用户前台焦点。
- **实现难度：** 中，代码可能少，但精度验证成本高。
- **最小实验：** 先旁路记录“本地建议”，不改变投递；用 DSH 真实前台/待答与用户纠正标签评估新增部分。合成冲突样例可证明规则边界，不能证明实际精度；没有可信标签时不扩大自动放行。

### 11. 完整状态指纹的结果缓存与在途请求合并

- **思路：** 对同一消息的重复事件、重试和多入口重复分类，按完整语义状态键复用结果；同键在途调用共享 promise。键含模型/模板版本、文本、有效目录修订、候选、当前话题、recent、foreground/pending/running、纠正、facts 和相关开关。投递使用另一层 messageId 幂等。
- **收益机制/估算：** 重复率 d、重算成本同分布时近似减少 d 的模型费用和网络等待。当前已能复用被后台接纳的 route，新增收益只来自尚未被覆盖的重复；首先测 d，不能先承诺 10%。
- **准确率/延迟风险：** 只按文本缓存“好”“继续”会串话题；TTL 不能替代状态失效。取消共享请求须有调用方引用计数，过期状态结果不能提交。复用随机模型结果也会减少重新抽样机会，但路由通常更需要稳定。
- **实现难度：** 中。
- **最小实验：** 同状态重复 100 次只产生一次假模型调用；再逐项改变 foreground、pending、目录修订、纠正、模型，必须失效。测试一个等待方取消不终止其他等待方，及重复消息只投递一次。语义近似缓存另行验证，不混入本方案。

### 12. 本地 embedding 检索，带拒判的小型语义闸门

- **思路：** 卡片变更时更新本地向量；新消息结合必要的前台状态检索，使用第一/第二候选差距、专名和冲突特征，只对高置信已有话题直接判定，其他交给 LLM。不为此使用付费 embedding API。
- **收益机制/估算：** 可同时减少候选输入和一部分调用。若新增放行 f，则远端费用收益按 10 的公式算，再扣本地加载、计算和存储。BGE-M3 提供多语言、多种检索表示的研究依据，但不证明中文话题路由能达到某个精度。[M3-Embedding](https://arxiv.org/abs/2402.03216)
- **准确率/延迟风险：** 同项目两项工作向量很近；“是”“按刚才的做”主要依赖状态；CREATE 与未知分布很难校准。本地首次加载可能慢于云请求。
- **实现难度：** 高，需要分布外拒判、跨时间校准和客户端资源治理。
- **最小实验：** 先只替换候选召回，不改变最终路由；按主题/时间隔离 dev/test，测 recall@k、低间隔拒判率和冷/热本地延迟。之后再评估高精度放行覆盖曲线，不直接把 cosine 当概率。

### 13. 按风险复核，翻页按需发，而非一律多发

- **思路：** 保留对强证据冲突、依赖缺失历史的保护；区分自足新请求与高风险 CREATE，尝试减少无效复核。剩余目录先发最有希望的一页，只有未解决时才继续；不把“高自信”自然语言当作校准概率。
- **收益机制/估算：** 若附加调用确实从 0.1/消息降到 0，则同分布简化上限约省 9.09%；若复核更长或思考更多，收益会不同。先前并发但未采用的页即使最终只用第一份，也已经产生费用。
- **准确率/延迟风险：** 少复核可能错建新题；串行翻页省 token 却增大最坏延迟。必须同时比较遗漏旧题、混入和 p95，不能只看 calls。
- **实现难度：** 中。
- **最小实验：** 分层统计“复核是否改判、是否改对、每页是否有独特贡献”；从低风险子集做旁路消融。并发三页与先一后续使用同一预算和同一候选集合做对照，避免把减少检索误报为缓存收益。

### 14. 稀疏输出协议、局部短 ID 与分级理由

- **思路：** 普通已有话题只输出动作和目标，缺省字段由本地补全；CREATE、关联导入和疑难场景再输出必要字段。以快照内稳定短 ID 映射真实 ID；必要时使用短理由码，保留抽样或疑难诊断信息。
- **收益机制/估算：** 当前 schema 要求多个空数组、null 和理由，若平均输出由 130 降到 60/30，前述官方价目情景可省约 22.73%/32.48%。这些目标长度需实测分词；短 ID 在高命中输入端的省费可能小，输出端更值钱。
- **准确率/延迟风险：** 删除 historyIndependent、relatedIds、imports 或项目字段的真实含义会损坏行为；缺省与“不知道”要区别。ID 映射过期会误投，必须带协议/epoch 版本并检查目录合法性。
- **实现难度：** 中，涉及提示词、解析和兼容，不能只删字段后期待旧解析器工作。
- **最小实验：** 先用既有合法判定离线做“压缩→还原”双向等价检查，覆盖全部动作和可选语义；再拟议相同输入的长/短协议成对模型对照。提前设置过短截断不能替代协议设计，避免 JSON 破损重试吞掉收益。

### 15. 卡片按语义事件更新，分离稳定身份与活动状态

- **思路：** 稳定卡只放“这件事是什么”，进展与待办放尾部；在新实体、用户纠正或任务阶段改变时更新稳定卡。后台合并连续写卡请求，旧卡生成结果不能覆盖更新后的 revision。
- **收益机制/估算：** 同时少发卡片请求、少让早期摘要改写。如果卡片占总账单 g、可合并一半，则直接省约 0.5g，另加未来缓存收益；g 未测，不把“少一半卡片”说成“少一半成本”。
- **准确率/延迟风险：** 卡片不及时会漏掉新的任务名和方向；仅保留标题也可能把两个同名任务混在一起。新信息应立即进入动态覆盖层。
- **实现难度：** 中。
- **最小实验：** 比较原有 1/4/每 8 次节奏、事件触发和带上限的合并策略；测卡片陈旧时间、候选召回、写入竞争与总费用。不要通过冻结一切摘要获得虚假的稳定前缀。

### 16. 在必需的 Worker 回复上附带路由元数据

- **思路：** 让本来就要产生的 Worker 输出附带轻量的任务身份、稳定卡修订或可续接关系；帮助下一轮判断，减少独立写卡。可用渲染前分离的结构化尾段，不能把内部字段显示给用户。
- **收益机制/估算：** 若能替代 k 次独立卡片调用，净收益为其成本减去新增输出和后续校验成本。对当前消息先选 Worker 的依赖仍在，不能宣称省掉当前这一轮的首次路由。
- **准确率/延迟风险：** 普通正文混入元数据、流式输出未结束、Worker 自报身份有偏差；也可能增加正文任务的失败率。跨话题线索不应变成授权。
- **实现难度：** 高，耦合 Worker 协议、流式与失败恢复。
- **最小实验：** 仅对假 Worker 输出做解析和渲染隔离测试；以后在一个可控 Worker 上试“附带卡片”，分别计新输出、遗漏卡片和重试，先不改变当前路由。

### 17. 微批处理：交互单流有严格上限

- **思路：** 对互不依赖的多入口、后台整理或已收齐的粘贴消息，一次发送公共目录和多个独立待判项；单一实时会话默认不等批。确需顺序语义时，模型输出的是带明确先后状态的事务，而非独立并行答案。
- **收益机制/估算：** 批大小 b、共享输入 S、每项独立输入 U，则每项输入约 S/b+U。S=2400、U=500、b=4 时由 2900 降到约 1100；但若 S 本来已经命中，应按缓存单价计算，节省远小于输入总数降幅。
- **准确率/延迟风险：** 等批增加首条等待；后条可能依赖前条 CREATE 得到的真实 ID；共享一次失败会影响整批。自动分条回退与原批重复费用都要计入。
- **实现难度：** 中至高。
- **最小实验：** 先做完全独立的 2/4 项假模型批次，验证 ID 映射、每项归属、部分失败与幂等。以后分别测吞吐与交互首条延迟，不用离线吞吐替代单用户体验。

### 18. 投机执行：先做可丢弃的本地准备

- **思路：** 路由期间并行准备最可能的话题的本地只读上下文、索引和界面资源；必要时试极短、可取消的模型前缀探针。最终路由确认前，不投递任务、不执行工具、不落下用户可见的错误回复。
- **收益机制/估算：** 可隐藏 min(准备耗时, 路由耗时)，但本身不提高服务端命中或减少调用。若命中概率 p、额外远端准备成本 W，浪费期望至少为 (1-p)W，另有取消后仍计费的风险。
- **准确率/延迟风险：** 投机目标错了要回退；提前启动真正 Worker 可能产生错误副作用。双发快/慢路由主要换尾延迟，模型调用数会上升。
- **实现难度：** 本地只读准备为中，远端双发为高。
- **最小实验：** 只用可取消的本地假任务，测被隐藏的时间、命中率和丢弃开销。把“双发”列为尾延迟专项，不包装成省 token 的主方案。

### 19. “是否仍属当前话题”小判定，再做全局检索

- **思路：** 第一层只看当前话题、真实前台状态和输入，输出 KEEP 或 DEFER；DEFER 才进入完整路由。可以用极小本地模型，或将第一层设计为带拒判的云端短请求。
- **收益机制/估算：** 云端两层的期望调用数为 1+p_defer，未必少于当前约 1.1；真正比较成本 C_small+p_defer×C_full。第一层放本地且足够准时更有吸引力。
- **准确率/延迟风险：** 顺从当前话题的偏差会掩盖换题，尤其同项目任务；DEFER 用户会多等一层。第一层必须允许拒判，不能强行二选一。
- **实现难度：** 中至高。
- **最小实验：** 从切题、同项目不同任务、否定和短回应的集合测“错误 KEEP 率—覆盖率”；先离线画阈值曲线，再决定是否值得增加云端一层。

### 20. 分层索引：本地宽召回，稳定小目录供判定

- **思路：** 用本地倒排、项目路径和向量做宽召回，再交给 LLM 小而稳定的候选集；候选不只由最近活跃决定，允许冷门旧题通过精确实体进入溢出区。必要时做局部 rerank，而非直接向云端发多个二分目录请求。
- **收益机制/估算：** 假设 16 张卡压到 6 张、每卡 60 token，可少 600 输入；若原本命中，直接账单收益仅约 12 单位/调用，真正更大的收益可能是少翻页。若候选抖动反而变大，命中率还可能下降。
- **准确率/延迟风险：** recall@k 是准确率上限；未召回旧题时模型很容易 CREATE。短输入和同名跨项目事项需要状态补充。
- **实现难度：** 中，仓库已有检索，要先测现有召回，避免另建同类索引。
- **最小实验：** 固定目录的人工冷门回访测试，比较现有 16、稳定 6+溢出、宽召回后重排；同时统计 miss、review、漏召回，而非仅比 payload 大小。

### 21. 换状态表示：本地维护任务信念与事件，不重复叙述

- **思路：** 将“正在执行、等待谁、用户看到了谁、临时插问后回哪题”等维护成小型状态机/概率信念；把明确事件在本地折叠，只将歧义候选及证据交给模型。稳定说明在前，少量离散状态在后。
- **收益机制/估算：** 状态输入从多段自然语言缩成 id、事件和有限枚举，可能压缩动态尾部；例如少 200 个未命中输入可省约 200 单位/调用，另可能减少复核。实际压缩量要按 tokenizer 算。
- **准确率/延迟风险：** 概率高不等于用户意图；后台完成不可自动抢前台，pending 不等于授权。纯隐状态模型会漏掉语义突然转向。
- **实现难度：** 高；当前绑定机制已有很多确定状态，只在无法表达的部分增量扩展。
- **最小实验：** 用人工事件序列验证同一时序在结构表示与现有语义下结论一致，包含插问、多个待答、关闭话题、恢复与通知乱序；不以删状态换小输入。

### 22. 自有推理网关：缓存亲和路由与多级缓存

- **思路：** 如果未来自托管小路由模型，将共享前缀请求送到保有 KV 的 worker，结合负载均衡及 GPU/主存等缓存层；可以用 SGLang 的 cache-aware 思路。仅在自己可控的 worker 上调度，不声称能控制官方 API 内部落点。[SGLang 网关](https://docs.sglang.io/docs/advanced_features/sgl_model_gateway)
- **收益机制/估算：** 理想 prefill 时间由 P/吞吐变为 M/吞吐，P=2900、M=667 时最多少处理约 77% prefill token；端到端还要加检索、队列、decode 和传输。vLLM APC 明确主要省 prefill，不减少新输出的 decode。[vLLM APC](https://docs.vllm.ai/en/v0.10.1/features/automatic_prefix_caching.html)
- **准确率/延迟风险：** 热点 worker 排队可能抵消缓存收益；模型替换会改变准确率。硬件、运维和利用率成本可能远高于便宜云路由。
- **实现难度：** 高；不属于此次文档任务的部署动作。
- **最小实验：** 将脱敏请求长度/前缀哈希做离线调度模拟，比较随机、轮询与缓存亲和的 hit/队列；有自有资源后再测实机。不能把模拟命中换成官方账单承诺。

### 23. 模块化 KV、可组合片段与预计算话题表示

- **思路：** 在自有模型服务中探索按 schema 预计算稳定模块，或用专用编码器把每题变成可复用表示，避免每次都依赖从序列起点精确匹配。Prompt Cache 研究提供了模块化 attention 复用方向。[Prompt Cache 论文](https://arxiv.org/abs/2311.04934)
- **收益机制/估算：** 若可安全复用 k 个稳定模块，新增计算可能只与变化模块相关；但标准自回归 KV 依赖前文和位置，不能把不同上下文下的 KV 直接拼起来。没有引擎与精度实验，不给百分比。
- **准确率/延迟风险：** 隔离注意力或重用位置会改变模型可见的信息；跨话题比较和指代可能变差。
- **实现难度：** 很高，需要引擎、注意力/位置设计和模型验证；官方兼容 API 没有本文可依赖的任意片段 KV 上传接口。
- **最小实验：** 先在自有小模型上对两个模块交换顺序、更新其中一个，比较普通完整推理与模块方案输出和延迟；把它列为研究，不作为客户端近期修复。

### 24. 蒸馏专用本地路由器，远端只处理拒判

- **思路：** 积累带真实状态与用户纠正的样本后，训练或蒸馏一个小分类/匹配模型，预测话题或拒判；远端处理复杂 CREATE、跨题和低置信情形。类别随目录变动，宜用候选打分而非固定话题分类头。
- **收益机制/估算：** 若经过校准的拒判率为 d，云端费用约为 d×原对应成本，另加本地推理和训练摊销。RouteLLM 支持“按难度选择模型”的研究思路，但其强弱模型选择任务不同，不能借用论文节省倍数作为 TheOne 的结果。[RouteLLM](https://arxiv.org/abs/2406.18665)
- **准确率/延迟风险：** 数据少、标签按窗口而非事情、伪标签错误与同项目偏差会一起被学进去；本地量化和跨机器冷启动也需验证。
- **实现难度：** 高，近期瓶颈是标签与拒判校准，不是先选一个模型。
- **最小实验：** 先只用人工合成和已授权纠正样本做离线时间隔离验证，报告选择性风险/覆盖率；没有足够真实金标时只做影子建议，不训练出一个模型就宣布能替代云端。

## 5. 专门核算“只追加历史能否做到 99%”

Reasonix 旧版官方仓库保存了一个 2026-05-01、单用户单日的案例：435,033,856 个命中输入 token、767,616 个未命中输入 token，按 token 加权为约 99.82%。这是项目公布的个案，不是本轮独立复现实验；旧版 v1 分支资料不能代表当前默认分支实现，也不能把当时美元价目套到今天。[Reasonix 原始案例](https://raw.githubusercontent.com/esengine/DeepSeek-Reasonix/v1/benchmarks/real-world-cache/README.md)

可以借鉴“保留不变前缀、追加新事件”，但要比较**完成同样路由工作的绝对费用**。长历史会让命中 token 的分母越来越大；这些 token 即使命中仍收费。压缩后生成的新摘要也会形成新内容，不能假设换代免费或自动保持全部旧前缀。

### 一个可复算的有界日志模型

以下是理想假设，不是当前插件实测：

- 基础快照 B=2400 token；
- 每轮新增输入 u=260，路由输出 a=130；
- 输出也加入下一轮历史，所以每轮增长 g=u+a=390；
- 每个 epoch 的首轮全冷；后续都能完整复用上一轮输入/输出，只有新增 u 未命中；
- 每 epoch n 轮，未额外调用模型压缩；无过期、逐出、模板漂移或失败重试；r=0.02、s=4。

~~~text
第 t 轮输入 P_t = B + u + (t-1)g
平均输入 P_avg = B + u + (n-1)g/2
平均未命中 M_avg = u + B/n
平均命中 H_avg = P_avg - M_avg
单次成本 V_call = M_avg + r×H_avg + s×a
~~~

对比同样输出 130、单次输入 2900、h=77% 的基线单次成本 1231.660。这里只比较单次主路由；额外复核与卡片另计，没有把一条共享日志假设套到所有并发分支。

| epoch 轮数 | 平均输入 token | 平均未命中 token | 加权命中率 | 单次成本单位 | 相对基线节省 |
|---|---:|---:|---:|---:|---:|
| 8 | 4025 | 560 | 86.09% | 1149.300 | 6.69% |
| 16 | 5585 | 410 | 92.66% | 1033.500 | 16.09% |
| 24 | 7145 | 360 | 94.96% | 1015.700 | 17.53% |
| 32 | 8705 | 335 | 96.15% | 1022.400 | 16.99% |
| 64 | 14945 | 297.5 | 98.01% | 1110.450 | 9.84% |
| 128 | 27425 | 278.75 | 98.98% | 1341.675 | -8.93% |
| 256 | 52385 | 269.375 | 99.49% | 1831.688 | -48.72% |

在这组假设里，99.49% 命中比 77% 基线反而贵约 48.72%。有限 epoch 的最优点约为：

~~~text
n* ≈ sqrt[ 2(1-r)B / (r×g) ] ≈ 24.56 轮
~~~

它只是忽略精度、延迟、过期和离散落盘后的成本最优近似；实际不应照抄 24。r 越大、单轮增长越大，越需要早换代；缓存很便宜且稳定时，才可能适合更长日志。缓存意外丢失时整段历史的重算风险随长度一起增加。

准确率还需防止模型只延续旧判定、不认真处理当前修订；长上下文的位置敏感性有早期研究依据，但不能把其他模型的结果直接当作 V4.1 的定量结论。[Lost in the Middle](https://arxiv.org/abs/2307.03172)

### 最值得先试的三个实验

1. **02：快照+覆盖层。** 从“候选集不变、内容语义不变”起步，做物化状态等价和前缀断点统计；只要覆盖层造成的额外成本抵消了 miss 减少，就淘汰当前编码。下一步才试固定候选池，避免同时改缓存与召回。
2. **14：稀疏输出。** 先证明压缩/还原保持全部判定语义，再拟议同输入的长短协议对照；验收看平均输出、无效 JSON/回退、误投和可见延迟，不用强制 max_tokens 截短伪造收益。
3. **11：完整状态缓存/在途合并。** 先测尚未被现有 route 复用覆盖的重复比例，并做逐字段失效测试。若可消除调用太少，停止扩展；用 13 的附加调用消融取代它成为第三项。

05 的有界日志作为下一组架构对照，候选 epoch 从 8/16/32 开始；本轮不实施。10、12、24 的影子路由应等待更可靠的真实状态标签，而非依据多窗口短句评分扩大自动 KEEP。

## 7. 最小实验与验收方法

### 阶段 A：无模型、无凭据，先验证结构

在已有授权范围内，仅需人工状态序列和内存假模型：

- 给每种实际模板、快照和动态尾部计算独立哈希；只保留长度、字段路径和哈希等最小记录，不把真实聊天导出到报告。
- 统计相邻请求和同簇历史请求的首变字段、最长公共 token/字节前缀、模板分叉、候选集合变化和写卡频率。字节前缀只作代理，缺少精确 tokenizer 时必须注明。
- 02 测物化状态等价与候选不变，14 测协议等价，11 测失效与幂等，05 测事件顺序、分支与恢复。
- 模拟“请求结束单元”“第二次发现公共单元”“异步构建”“逐出”等多种缓存模型，只给敏感性区间，不把其中某一种当作官方内部实现。
- 保留 2900/130/1.1/77% 情景作为计算参照，不拿旧工具的字符估算结果覆盖这个任务基线。

现有 prefix-share 的三项测试可验证其既有算法，但该算法按最大历史公共前缀立即复用、64-token 估算；它没有真实落盘时序，也会依据金标推进模拟目录。其测试通过，证明不了新缓存机制或在线准确率。将来修订评测器须另行任务授权，本轮不改它。

### 阶段 B：未来获准后，才做小型服务端探针

本轮没有执行以下任何请求，也没有为此读取或索取 Key。

先在实际使用的同一端点、同一模型/模式上，用人工无敏感文本测：

| 探针 | 要辨别的问题 |
|---|---|
| A+B → A+B+C | 是否能复用完整已结束单元 |
| A+B → A+C → A+D | 公共部分何时可用，不能把“两次预热”当普遍定律 |
| 同样内容，改变角色/消息边界 | 客户端切段是否保留预期的模型前缀 |
| 相同序列，间隔 0/2/5 秒 | 异步构建是否解释连续冷 miss |
| 相同前缀，串行与有限并发 | 并发冷启动是否重复付费 |
| quick 与 recheck 的真实参数组合 | 是否确实共享缓存，而非只在字符串上相同 |
| epoch 8/16/32、冷/热启动、空闲后重返 | 全流账单与过期风险，避免仅截取高命中尾段 |

所有探针请求、输出、等待、失败、重试和预热均进账。官方 API 返回 usage 是命中依据；如果兼容端点不暴露它，就把该项记为不可观测，只讨论账单/延迟，不能反推一个精确命中率。

### 阶段 C：结构收益成立后，验证产品准确率与延迟

[现有真实聊天评测说明](routing-real-chat-benchmark.zh.md)最后记录：多窗口语料缺少用户当时看见的前台状态，能观察混入，但不足以证明短回应的切换正确；已记录的 DSH 用户纠正标签仍为 0。这个记录不是本轮扫描用户数据的结果。不能拿“永远 KEEP”在这类数据中的表面稳定性支持新的本地快路。

- **数据：** 优先使用带事件时间、真实 foreground/pending、用户纠正的 DSH 样本；按会话/时间隔离训练、dev 与 test。没有前台信息的短句另列不可判定，不当作有确定金标。脱敏不等于匿名。
- **回放：** 先用固定状态带做单因素结构对照，再做按各自预测推进状态的闭环回放，发现误路由级联。金标不进入待判文本、候选说明或训练外测试提示。
- **主质量指标：** 高伤害跨任务混入、纠正后再次误投、旧题漏召回、无必要拆分；新增快路单独报错误率和覆盖率。不能只看总体正确率，也不能只看 CREATE 数下降。
- **延迟：** 同时报路由端到端、远端调用、队列/重试、本地冷加载及可见回复起始的 p50/p95；缓存主要改善 prefill，短输出、快速失败和少调用也可能更有用。
- **对照：** A→B→A 检查时间漂移，配对序列并交换顺序重复；共享相同前缀的实验可能互相预热，不把这种串扰当作方案收益。使用等价长度的独立人工前缀构造可区分的缓存簇，并分别报告冷/热；不能假称能清空官方缓存。
- **统计：** 按独立会话聚合，给分母、重复轮次和区间；现有少量流不足以许诺稳定的百分点改善。阈值只在 dev 调，test 不回调。

可预先设一条工程筛选线：总费用至少减少 10%、高伤害混入无可接受范围外增加、p95 可见等待不变差，才进入下一阶段。10% 是候选淘汰阈值，不是统计显著性或性能保证；必须先定义可接受的风险界限。

对新增本地放行，若要求错误概率约低于 0.5%，在独立样本且观察到零错的理想情况下，一侧 95% 上界为 1-0.05^(1/n)，约需 600 个放行样本。真实消息有关联、分布会漂移，应按会话检查并保留拒判；“跑了几十条没错”不足以支持高覆盖自动放行。
