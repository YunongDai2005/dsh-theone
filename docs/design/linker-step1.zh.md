## 目标与边界

新话题可以随便开，开得越小越不容易污染。每个话题都能**精确拿到别的话题里已经确认、仍然有效、允许共享的东西**，并带着证据和版本。

第一步的承诺比第一版收窄了：**宁可少给，不可给错。** 进入其他话题的只能是有用户证据的确认事实；拿不准的一律不出本话题。

第一步包含：

1. 有确认依据的要点记录（事实、决定、产物位置），可以撤回。
2. 写入使用乐观并发控制：过期的写入一律拒绝。
3. 按需导入，在**实际交付时**统一做权限检查。
4. 每次给后台会话交付内容前，检查它依赖的要点版本，**包括快速通道**；变了或撤回了就提示。
5. 交付事件日志与当前依赖关系分开保存，删除有明确策略。

第一步不包含：话题分叉和谱系；向量检索；自动提取（代码会写好，但默认关闭，验收通过后再开）。

## 一、数据结构（`src/store.ts`，同一个 SQLite）

**身份和版本分开存**：一件事实的身份是稳定的，版本只追加不修改；「当前版本」由身份行上的指针决定，所以结构上不可能出现两个当前版本。

```sql
-- 事实身份：一个话题里同一个 key 只有一行
CREATE TABLE IF NOT EXISTS facts (
  id TEXT PRIMARY KEY,                 -- fact_<随机>，跨版本、跨合并保持不变
  context_id TEXT NOT NULL,
  key TEXT NOT NULL,                   -- 规范化名称，见下文
  label TEXT NOT NULL,
  aliases TEXT NOT NULL DEFAULT '[]',  -- JSON 数组，元素同样规范化
  kind TEXT NOT NULL CHECK (kind IN ('fact', 'decision', 'artifact')),
  current_version INTEGER NOT NULL,
  merged_from TEXT,                    -- 合并时原属的话题 ID
  deleted_at INTEGER,                  -- 墓碑：来源话题删除后只保留身份，不保留内容
  UNIQUE (context_id, key)
);

-- 版本：只追加
CREATE TABLE IF NOT EXISTS fact_versions (
  fact_id TEXT NOT NULL REFERENCES facts(id),
  version INTEGER NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('confirmed', 'proposed', 'retracted')),
  value TEXT,                          -- 撤回时为空；最多 300 字，已脱敏
  evidence TEXT NOT NULL,              -- JSON：{ sessionId, seq, speaker, quote }，见第二节
  origin TEXT NOT NULL CHECK (origin IN ('worker', 'extractor')),
  created_at INTEGER NOT NULL,
  PRIMARY KEY (fact_id, version)
);

-- 交付事件：只追加，一次交付一行，可以重复交付同一版本
CREATE TABLE IF NOT EXISTS fact_deliveries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  context_id TEXT NOT NULL,            -- 接收方话题
  fact_id TEXT NOT NULL,
  version INTEGER NOT NULL,
  input_id TEXT,                       -- 触发的主聊天消息；后台会话主动查阅时为空
  via TEXT NOT NULL CHECK (via IN ('route', 'lookup', 'notice')),
  at INTEGER NOT NULL
);

-- 当前依赖：接收方最后一次看到的是哪一版
CREATE TABLE IF NOT EXISTS fact_dependencies (
  context_id TEXT NOT NULL,
  fact_id TEXT NOT NULL,
  version_seen INTEGER NOT NULL,
  first_at INTEGER NOT NULL,
  last_at INTEGER NOT NULL,
  PRIMARY KEY (context_id, fact_id)
);
```

**写入一律放在事务里**（`BEGIN IMMEDIATE … COMMIT`）。node:sqlite 是同步调用，加上事务，就保证「读当前版本、比较、写入新版本、移动指针」是原子的。

**规范化名称**：NFKC 归一，转小写，合并连续空白，只去掉首尾的引号和标点。保留 `+ # . - _ /`，所以 `C++`、`C#`、`.NET` 互不相同。写入时**只做精确匹配**：key 或某个别名完全相同。不做模糊合并，判断是不是同一件事交给模型，由它显式传 `factId`（见第二节）。

## 二、写入：确认依据、并发保护、撤回

### 1. 状态的含义

| 状态 | 含义 | 能否进入其他话题 |
| --- | --- | --- |
| `confirmed` | 有可核验的用户证据 | 能（还要通过权限检查） |
| `proposed` | 只有助手或工具的说法，例如「建议预算 800」 | **不能**。只在本话题内显示，并标明「建议，未确认」 |
| `retracted` | 用户表示撤回或尚未确定 | 不能；依赖它的话题会收到撤回提示 |

### 2. 证据由系统核验，不信模型的说法

每条写入都要附 `evidenceQuote`，也就是原话片段。系统在本话题后台会话最近的事件里找到这段原话（规范化后做子串匹配，数字统一格式），取出它的**说话人**和事件序号：

- 原话出自**用户消息**，并且包含要记录的值：记为 `confirmed`。
- 原话出自用户消息，表达对某个建议的明确接受（例如「好，就按这个来」），并且附带 `acceptsQuote` 指向助手消息里的建议值：记为 `confirmed`。证据里两段都保存。
- `artifact`（文件路径、链接等产物位置）可以用工具事件作证据：文件确实是工具写出来的。
- 其他情况，包括原话找不到、出自助手、值不在原话里：一律记为 `proposed`。
- 证据本身也要脱敏，最多 200 字。

这样，「助手建议的预算」不可能在没有用户确认的情况下变成跨话题的事实。

### 3. 写入工具 `theone_record`

```text
theone_record(items: [
  { op: 'set',     factId?, label, kind, value, aliases?, evidenceQuote, acceptsQuote?, expectedVersion? },
  { op: 'retract', factId,  evidenceQuote, expectedVersion? }
])   每次最多 8 条
```

- 工具会把本话题已有的要点连同 `factId` 一起列给模型看（放在话题描述里，见第四节），模型更新已有事实时传 `factId`。
- `expectedVersion` 是模型最后看到的版本。省略时取写入那一刻的当前版本，这对同步发生的工具调用是安全的。
- 返回值逐条说明结果：已确认 / 记为建议（以及原因）/ 已撤回 / 因版本已变被拒绝（附当前值）。

### 4. 并发保护：过期写入一律拒绝

每次写入都是「比较后再写」：在事务里，如果事实的当前版本不等于 `expectedVersion`，就拒绝。

另有一条单调性规则：新证据在后台会话里的位置**早于**当前版本的证据时，同样拒绝。即使没有传 `expectedVersion`，较早一轮的结果也不会盖掉较新的值。

自动提取（默认关闭）在任务**开始时**记下每个相关事实的版本，提交时按上面的规则检查。同一个话题的提取任务排队串行执行，一轮的提取任务如果晚于后一轮完成，就会被单调性规则挡住。

审计里举的例子（第一轮的 800 晚于第二轮的 700 返回）：800 的证据在 700 之前，所以被拒绝，当前值仍是 700。

### 5. 撤回

`op: 'retract'` 写入一个新版本，状态为 `retracted`，值为空，证据必须来自用户消息（例如「预算还没定」）。撤回后，这个事实不再被导入或查到；依赖它的话题在下一轮收到撤回提示（见第四节）。

### 6. 合并与删除

- **合并话题**：把来源话题的事实移到目标话题，`fact_id` 不变，所以依赖关系不受影响。key 冲突时（两边都有「预算」）**绝不自动合并值**：来源一方的 key 加后缀、label 改成「预算（来自 某话题）」，并记录 `merged_from`。
- **删除话题**：删除它所有版本的值和证据，身份行留作墓碑（`deleted_at`）。依赖它的话题在下一轮收到一次「来源话题已删除，之前引用的值不再可用」，之后删掉这些依赖关系。被删话题自己的交付记录和依赖关系一并删除。交付日志里指向墓碑的行保留，只能追溯到「已删除」。

## 三、导入：权限在交付时统一检查

### 1. 唯一的权限函数

```ts
canShare(sourceContextId, targetContextId): boolean
```

**每次调用都读最新设置**，以下条件全部满足才返回 true：

- 来源话题不是「不共享」。
- 两个话题之间没有用户手动解除的关联（manual = -1）。
- 联动范围允许：「关闭」时一律不允许；「仅同一工作区」时两个话题必须在同一工作区。
- 事实没有被删除，当前版本是 `confirmed`。

所有出口都要经过它：路由导入的交付、`theone_lookup` 的返回、版本变化提示。**不在召回时做最终判断**，召回阶段的过滤只是为了减少候选，不能代替交付时的检查。

### 2. 召回候选（不调用模型）

在 `route()` 里，用消息加最近两条消息的字符特征（`textFeatures` / `similarity`），对其他话题的当前 confirmed 事实打分。再加上话题关联分、消息里提到话题标题时的加分，以及最近使用的加分。

召回时对「当前话题」做一次初步过滤，只是为了减少候选。这一层做成独立函数，以后加向量召回只换这一层。

### 3. 路由顺手挑选，有总量预算

路由请求里新增 `symbols` 字段，**整节不超过 1200 字符**（约 400 个 token）。单条的名称最多 40 字、值最多 80 字，最多 12 条，哪个上限先到就停。提示词新增一句，输出新增 `imports`（最多 5 个）。`validateRoutingDecision` 只保留候选里出现过的 id。

### 4. 交付

路由结果最终确定之后（包括「分错了」重新分配的情况），在给最终话题构建参考消息时：

1. 对每个 `imports` 重新调用 `canShare(来源, 最终话题)`，并重新读取事实的**当前**版本。不通过的直接丢弃。
2. 通过的写进参考消息的「要点」一节（整节不超过 1200 字符）：

   ```text
   本轮用到的其他话题要点（引用资料）：
   - 【社区读书会筹备】预算 = 700（第 3 版，用户于 10-03 14:20 确认）
   ```

3. 写入 `fact_deliveries`（`via = route`），并更新 `fact_dependencies.version_seen`。

### 5. 主动查阅 `theone_lookup`

```text
theone_lookup(query, topicId?)   最多 10 条
```

只返回通过 `canShare(来源, 本话题)` 的 confirmed 事实，规则和路由导入完全相同，包括用户手动解除的关联。返回的每一条同样记交付日志（`via = lookup`）并更新依赖。

## 四、使用前的版本检查（覆盖快速通道）

每次给后台会话交付输入之前，**不管走不走快速通道**，都检查这个话题的 `fact_dependencies`：

- 当前版本号大于 `version_seen`，且仍然可以共享：提示「预算：800 → 700（第 3 版）」。
- 已撤回：提示「预算：已撤回（用户表示尚未确定）」。
- 来源已删除，或者不再允许共享：提示「之前引用的〔名称〕不再可用」。**只说名称，不给新值**，避免权限变化后漏出内容。

提示放进本轮的参考消息，整节不超过 600 字符。发出后更新 `version_seen`，并记交付日志（`via = notice`）。这一步只查数据库，不调用模型。

审计里的例子（B 记着 800，A 改成 700，B 收到「继续」走快速通道）：B 在这一轮会收到变更提示。

本话题自己的要点，以 `factId`、版本和状态的形式放进话题描述，最多 20 条、1500 字。其中建议状态的标为「建议，未确认」。这样后台会话写入时能引用 `factId` 和版本，压缩之后确定的值也不会丢。

## 五、脱敏与模型选择

- **发给模型之前就脱敏**：路由请求里的 `symbols`，以及自动提取请求里的用户消息、助手回答、已有要点，在组装请求时都经过 `redactRoutingText`。
- **写库之前再处理一次**：label、aliases、value、evidence 的每一个字段。
- **输出之前再处理一次**：参考消息、查阅结果、提示。即使库里有旧数据漏网，也不会再送出去。
- **模型选择**：在 0.3.20 里，单独配置的旧版直连路由已经移除（`routerTransport` 等设置只是为了兼容旧配置而接受，会被忽略）。路由一律使用 `backingModel()`，也就是用户通过「后台」按钮或设置选定的后台模型，与后台会话用的是同一个模型。自动提取同样只用 `backingModel()`。规则路由模式下不提取。

## 六、自动提取：写好，默认关闭

设置项「自动记录要点」，可选值为关闭（**默认**）/ 开启。开启后，每轮在 `finishRun` 里异步执行一次：

- **输入预算**：整个请求不超过 6000 字符。本轮的用户消息和助手回答按比例截取，已有要点不超过 1500 字符。
- **输出要求**：输出的每条都必须带 `evidenceQuote`，经过和工具完全相同的核验、并发检查和权限规则。
- **成本**：每轮约 2.5 千 token 封顶。

等第七节的验收通过，再讨论是否默认开启。

## 七、验收标准（第一步的发布条件）

### 必须通过的测试（使用真实的 DSH 运行时和模拟模型，和现有 `tests/` 一样）

1. 助手说「建议预算 800」，用户没有确认：记为 `proposed`，不会被导入，也不会被查到。
2. 用户说「好，就按 800」：记为 `confirmed`，证据里同时有接受语和建议原话。
3. 过期写入：任务以第 1 版为基准时，另一处已写入第 2 版，任务的提交被拒绝，当前值保持第 2 版。较早证据晚提交时同样被拒绝。
4. 撤回之后不再被导入或查到；依赖它的话题下一轮（包括快速通道「继续」）收到撤回提示。
5. 权限变化：召回之后、交付之前，把来源话题标为不共享、手动解除关联或关闭联动，都不会交付；`theone_lookup` 拒绝返回；依赖提示只给名称，不给值。
6. 唯一性：并发写入同一事实不会产生两个当前版本（由结构约束和事务保证）；`C++` 和 `C#` 是两个不同的 key。
7. 合并：同名事实保留两条，不合并值；依赖关系保持不变。删除：留下墓碑，依赖方收到一次提示，之后依赖关系被清除。
8. 脱敏：用户消息里的密钥不会出现在自动提取请求里（检查模拟模型收到的内容），也不会出现在任何存储字段里。
9. 预算：符号一节、要点一节、提示一节、提取请求，各自都不超过上限。

### 必须达标的基准测试（InterleaveBench）

- **路由不退步**：两种模式的分对率和串话题率不低于当前版本（`fda7f62` 的这次测量）。
- **跨话题事实题**：答对率高于「现有摘要式参考」这个对照组。
- **过时题**：用了旧值的比例低于 5%。
- **建议冒充事实**：助手建议被当成跨话题事实使用的次数为 0。

「路由不退步」按同一份数据、同一请求在「提供要点候选」和「不提供」两种情况下各路由一次来衡量：不提供候选时，路由提示词和请求与当前版本完全相同，所以两者选择的话题不同的比例（门槛：低于 2%）就是这项功能带来的退步。

这意味着**基准的第二阶段要提前**：补上助手回复（其中要有「助手建议、用户确认或否决」的情节），以及模拟回答的评测脚本。它们在第一步发布之前完成。

## 附录：审计意见对照

| # | 审计意见 | 处理 |
| --- | --- | --- |
| 1 | 「已确认」缺少确认依据 | 新增状态和证据；证据由系统在事件里核验说话人；只有助手说法的记为 proposed，不出本话题（第二节第 1–2 小节） |
| 2 | 后台提取可能用旧值覆盖新值 | 写入时比较版本；证据位置单调；提取任务串行（第二节第 4 小节） |
| 3 | 权限没有覆盖最终导入和主动查阅 | 唯一的 `canShare`，在交付时读取最新设置；查阅、提示一律适用（第三节） |
