日期：2026-11-04。费用都是把同一批 token 按公开价格重新折算。不是历史账单，也不是模型实测收益。

**对已经会手动分会话的人，这批数据没有显示 TheOne 基线更省钱。** 在 100 万窗口、1 小时缓存下，TheOne 按 DeepSeek 价格约花 **$4.50**，手动分会话约花 **$4.16**，多花 **8.27%**。相对一直聊下去的单会话，则省 **34.99%**。

## 计算方法

每次请求的总输入 = 普通输入 + 缓存写入 + 缓存读取。下文“未命中输入”包含前两项。

相邻调用之间的新输入 = 本次总输入 − 上次总输入 − 上次输出。一轮增长量 = 它的全部新输入 + 全部输出。轮内偏移按这个顺序累计。各策略使用相同的增量、调用次数、输出和时间；只改变历史放在哪个会话、压缩与缓存，以及 TheOne 的额外开销。

日志没有单独标记完整系统和工具提示的 token。先以首条用户文本的 UTF-8 字节数除以 3，估算其输入；首个请求扣掉这部分，作为固定提示开销。20 个会话的估计范围为 **53,907–77,156 token**。主比较统一采用会话中位数 **63,933 token**，让各策略的固定输入相同。另算保留原会话开销、统一 4,096 和统一 65,536 的敏感性。这个初始拆分是估计，不表示 DSH 的系统提示真的这么长。

缓存只复用上一次请求已输入过的前缀。输出要等后续请求再次输入，才成为可缓存内容。超过 TTL 失效；刚好等于 TTL 仍算命中。不同会话最多共享 **4,096 token** 的系统前缀。这里假设前缀相同，未测服务端是否真的命中。时间使用回复记录时间，近似请求时序。

### 压缩和简报

采用已安装 DSH 实现的预算公式：触发阈值取“窗口的 80%”与“窗口减输出预留、再减安全余量”的较小值。安全余量采用实现默认的 **65,536**；每次输出预留假设 **8,192**，可改参数。近期历史保留预算是“窗口减输出预留”的 **16%**。

100 万窗口在 **800,000 token** 触发，保留约 **158,689** 的近期历史；20 万窗口在 **126,272** 触发，保留约 **30,689**。固定系统提示继续存在，再加 **2,048 token** 的摘要。摘要指令按 **600 token** 估计。

压缩调用只发送被替换的历史前缀及系统提示、工具定义和摘要指令，输入与输出全部计费。近期保留部分不重复送去做摘要。新的摘要指令不能算缓存命中。压缩后下一次 Worker 请求按冷缓存计。

这是 token 预算近似。真实实现按整条消息保留，并保护工具调用配对；只有 usage 无法还原每条消息的 token 边界。没有模拟压缩失败、重试和溢出恢复。

Worker 注入由固定说明、话题描述、进展、可选事实及恢复说明组成。描述默认字符预算是 **4,000**，不等于 4,000 token。主估计每次实际启动 Worker 注入 **1,000 token**，留在后续历史中。当前实现每轮都会注入；任务说明的“仅新话题注入”另作敏感性。还算了每轮 0、500、2,000 token。

## 哪些假设最重要

**窗口和保留预算最能改变方向。** 100 万窗口让单会话反复携带大量旧内容，分会话能少带一些。20 万窗口更早删掉历史，差距缩小，某些档位反转。便宜同时意味着更频繁丢弃原始历史；这里没有给质量损失定价。

**TTL 明显影响绝对费用。** 日志实际写入 1 小时缓存。5 分钟档会把部分现实中的命中算成冷输入，不能把该档较大的美元差额当成已验证收益。

## 局限与判断

- 主样本没有话题映射，不能说明 TheOne 的真实路由准确率或实际话题数量。
- 不能说拆得越多越好。拆开删除了可用历史，所以可能更便宜；恢复历史的成本和回复质量没有重跑。
- 原回复固定。压缩、串话、上下文减少对正确率与输出长度的影响都没计。
- 主样本来自一位作者的 Claude 编程代理，工具输出与固定提示很大，不能直接外推到日常 DSH 聊天。
- 缓存采用理想化规则。服务端分块、最小长度、驱逐、提示变化及真实请求起止时间没有复原。不同分词器也会改变 token 数。
- 没有模拟排队、压缩耗时和单 Worker 的并发限制，不能据此声称速度提高。
- 记账重建的 0% 误差不等于费用预测完全准确。最接近日志的 1 小时、100 万窗口档仍有约 3.7% 费用偏差。

这批数据中，TheOne 基线相对已经手动分会话的作者更贵。相对从不开新会话的人，在大窗口假设下可能省钱。小窗口下节省很小或变成多花。它是否值得，不能只由这份 token 估算决定。
