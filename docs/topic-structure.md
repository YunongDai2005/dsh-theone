# 话题的组织结构：参考社区的项目分类和任务看板

起因：2026-10-11 调研了 DSH 社区的两个插件。这里只学它们的**数据和组织结构**，界面不模仿。TheOne 的界面仍按自己的设计语言来：用户不管理看板，结构由 TheOne 在后台维护。

- **Worktree 插件**（`@cerbur/clutch-dsh-worktree` 0.1.17）：按「项目 → 主目录 / worktree → 会话」组织会话。
- **任务看板**（`@linxin666/dsh-client-ui-task-board` 0.4.6）：按「项目分区 → 任务（状态、子任务、标签）→ 执行记录」组织工作。

这是结构性改动，**等确认后再动代码**。

**进度（2026-10-11）：** 用户确认先做第 1 点和第 3 点，已在 0.3.32 实现：话题有了项目维度（从 DSH 工作区推出），状态和执行记录分开保存，重启时把没跑完的执行记为「中断」。实测还发现：DSH 关机时会把主聊天队列里没轮到的消息直接取消（普通会话也一样），所以「后台已开工、重启后还在队列里」的情况在当前 DSH 不会出现，对应的说明只作兜底。第 2、4、5 点还没做。它同时是 `docs/execution-boundaries.md` 第 1 项（资源隔离）、第 2 项（恢复）和第 4 项（话题粒度）的地基。

## 现在的结构

- **话题**（`contexts`）：一层，平铺。每个话题有标题、摘要、实体、关键词，以及一段自由文本的「最新进展」（`lastState`）。
- **分组**（`topic_groups`）：可选，一个话题最多属于一组。目前只用于把历史里互相关联的话题归在一起。
- **项目**：只隐含在「话题从哪个文件夹来」（`context_origins.cwd`）里，不是一个可以查询的维度。
- **状态**：只有路由时临时算出来的「活跃程度」（「3 小时前」「已搁置 12 天」），不存。没有「做完了」「在等你」「中断了」这些状态。
- **执行记录**：每条消息一条路由记录（`routing_events`，状态只有 planned / running / completed / failed）。这些记录挂在消息上，不挂在话题上，也没有上限。

## 他们的结构里值得学的六点

### 1. 项目是第一层，而且来源唯一

- **他们怎么做：**
  - 两个插件都以 DSH 注册的工作区作为「项目」，不自己发明项目。
  - 任务看板有「全部项目」和单个项目两种视图。没有指定项目的任务，继承创建它的那个会话所在的项目。
  - Worktree 插件在项目下面再分一层：主目录和各个 worktree。
- **学过来的做法：**
  - 话题加一个明确的 `projectId`：
    - 取值是 DSH 的工作区，或者「无项目」（DSH 默认工作区和主聊天文件夹都算这一类）；
    - 现有话题按 `context_origins.cwd` 推出来；
    - 新话题用路由选出的项目文件夹（0.3.27 已有）。
  - 项目只从 DSH 读取，TheOne 不建、不改。
- **用处：**
  - 写操作排队（资源隔离阶段 0 和阶段 1）按项目判断；
  - 路由时同一项目的话题优先成为候选；
  - 一句话固定归属（「接下来都是 proj 的事」）固定的是项目。

### 2. 目录绑定：每次执行时现算，坏了就报错，不悄悄换地方

- **他们怎么做（Worktree 插件）：**
  - 会话在哪个目录跑，每次执行时现算，不写回 DSH 的会话元数据。
  - 一个会话最多绑定一个 worktree，一个 worktree 可以挂多个会话。
  - 绑定有健康状态：正常、分支偏了、需修复。失效时**绝不悄悄退回主目录**。
- **学过来的做法：**
  - 话题和工作目录之间建一条「绑定」：项目，加上可选的 checkout（主目录或用户已有的某个 worktree）。每次开工时现算目录。
  - 目录不在了，或者分支被外部切走了，就在主聊天里说明，不偷偷换到默认工作区。
  - **TheOne 不自己建 worktree**，只认用户已经有的。

### 3. 状态和执行记录分开

- **他们怎么做（任务看板）：**
  - 任务有一个状态：待规划、待办、进行中、已完成、已失败。另有一个独立的「归档」标记。
  - 每次执行是单独的一条记录，任务状态由**最近一次执行**推导出来。
  - 用户手动改状态只改状态本身，不伪造执行记录。
  - 正在执行的任务，结算前不能改状态。
  - 每个任务只保留最近 20 条执行记录。
- **学过来的做法：**
  - **话题状态**，存下来，由 TheOne 维护：
    - 进行中；
    - 在等你（有授权、提问，或者中断后等你说「继续」）；
    - 搁置（很久没动，不进路由候选，但能搜到，再提到时自动回到进行中）；
    - 完成；
    - 归档（独立标记，可以恢复）。
  - **执行记录**，挂在话题上，每个话题只保留最近 20 条。每条记录：
    - 对应哪条消息；
    - 结果：完成、失败、中断、分错已转走；
    - 有没有改动过东西，改了哪些文件；
    - 话题会话里对应的范围。
  - **推导规则：**
    - 话题状态由最近一次执行加上用户的明确说法共同决定。
    - 用户说「这件事做完了」，TheOne 直接改状态，不伪造执行。
    - 正在跑的话题，等这一轮结束后再改状态。
- **用处：**
  - 重启恢复：「中断」就是一条执行记录；
  - 「分错了」的闭环：标记那一条执行，摘要和简报跳过它；
  - 话题生命周期：完成、搁置、重新打开都有了明确的含义。

### 4. 进展写成「目标 / 进度 / 下一步」

> **进展（2026-10-18）。** 已做：话题可以按三项保存现状（`theone_update_state` 的 `goal` / `progress` / `next`，每项不超过 300 字，只给一项时其余保留），原来的 `lastState` 由三项自动拼出（中英文标签跟着内容走），所以路由、简报、目录这些现有读取方不用改；话题开工时的简报直接带三项。仍可写一段自由文本，写了就替换掉三项，两者不会不一致。历史目录重新抽取时保留话题自己写的三项。

- **他们怎么做（任务看板）：** 续接一个任务时，带一份冻结的「目标、进度、下一步」快照，每项有长度上限，敏感内容会被替换掉。
- **学过来的做法：**
  - 把 `lastState` 从一段自由文本改成「目标 / 进度 / 下一步」三项。
  - 话题开工时给模型的简报、中断后说「继续」、拆分话题，都直接读这三项。不用再从一段文字里猜现在做到哪了。

### 5. 层级很浅，有上限

- **他们怎么做（任务看板）：** 子任务默认只有一层，最多三层，而且不能挂到自己的后代下面。
- **学过来的做法：** 对应 `execution-boundaries.md` 第 4 项的三种粒度。
  - 层级：**项目 → 长期事项 → 具体任务**，事项下面最多一层任务。
  - 现有的「分组」升级为「长期事项」。
  - 临时问答不进这个结构。
  - 拆分话题（`docs/proposals.md` 第 2 项）就是在同一个事项下新建一个任务。

### 6. 数据账本的规矩

- **他们怎么做：**
  - 数据存在宿主端，界面只显示宿主确认过的状态，带版本号；
  - 同一时间只允许一个进程写入；
  - 文件损坏时把原文件改名保留，绝不用空数据覆盖；
  - 请求带 id，重试不会重复执行；
  - 重启规则是确定的：已经有会话的执行，重启后继续观察；还没建会话就被中断的，取消，不重发。
- **学过来的做法：**
  - TheOne 已经用 SQLite 加事务，大部分规矩已经满足。还要补两条：重启对齐规则，和同一个数据库只允许一个进程写入。
  - 重启规则直接照抄。它比 `execution-boundaries.md` 里写的更简单，可以替换那里的规则：
    - 有话题会话的执行，重启后继续观察，或者读会话判断它停在哪；
    - 没有会话就被中断的，取消，不重发。

## 不学的

- **界面：** 看板、拖动卡片、侧边栏树都不学。TheOne 的用户只在主聊天说话；话题工作区只作为查看和纠正的地方。
- **让用户维护的东西：** 用户手动建任务、设定时运行、管标签都不学。TheOne 的状态由它自己从对话里维护，用户只在想纠正时说一句话。
- **TheOne 自己建 worktree、改 git：** 不做，违反「不改用户的东西」。

## 迁移

- 现有话题的项目从 `context_origins.cwd` 推出来；推不出来的归为「无项目」。
- 状态：最近 14 天动过的算「进行中」，否则算「搁置」。没有话题会被直接标成「完成」。
- 现有的「最新进展」原样放进「进度」一项，等下一次整理时再拆成三项。
- 执行记录从 `routing_events` 按话题回填最近 20 条。
- 新表都只加不改。关掉 TheOne 后 DSH 不受影响，装前关后没有区别。

## 需要你决定

1. **层级：** 「项目 → 长期事项 → 具体任务」三层可以吗？还是只要「项目 → 话题」两层，长期事项以后再加？
2. **状态：** 进行中、在等你、搁置、完成、归档这五个够不够？「多久没动算搁置」用 14 天可以吗？
3. **worktree：** 只识别用户已有的 worktree、TheOne 不建，这个方向对吗？
4. **顺序：** 先做第 1 和第 3 点（项目维度、状态和执行记录分开）。它们是资源隔离和重启恢复的前提。可以吗？
