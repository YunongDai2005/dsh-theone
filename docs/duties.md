# 职责：TheOne 做成 DSH 的 dot 的第一步

状态：2026-10-18 用户要求在现有结构上开始做；「要用户决定的」四条暂按建议执行，用户可随时改。第 1 步已完成。背景和对照见 `docs/dot-research.md`。

## 要做的事

dot 最核心的东西是"职责"：交给它一件持续的事，它在两次对话之间也一直在做。TheOne 现在的"持续任务"（0.3.36）已经会定时去看一个 GitHub PR，但只读、只给建议，不动手。

职责在持续任务上加四样东西：

1. **派单。** 需要动手时，交给这件事所属的话题会话去做。话题就是 TheOne 的"线程"，和 dot 把活派给 Codex 线程一样。
2. **授权。** 职责派出去的回合默认"先问再做"：要改文件、跑有影响的命令时，照现有的转发在主聊天或手机上问你。
3. **验收。** 创建时写清楚"做成什么样算完成"；只有核对通过，才说"完成"，并附上证据。
4. **提醒。** 只在需要你决定、做完了、出新问题时找你；绑定了手机入口时也发到手机。

## 第一个例子

> 「盯着这个 PR，CI 挂了就查原因，先问我再改。」

1. 你在主聊天或微信里说。消息照常分到这个项目的话题，话题创建一件职责：来源是这个 PR，验收标准是"新提交上的 CI 通过"，授权是"先问再做"。
2. 职责照持续任务的方式，每 15 分钟读一次 PR 和 CI 摘要（现成）。
3. CI 从通过变成失败时：职责不只是发建议，而是**派单**。给所属话题送去一轮工作，内容是目标、失败的检查、验收标准，以及"先查原因，改代码前先问"。主聊天里照常显示这个话题在做什么，和后台话题一样。
4. 话题会话照普通会话干活，工具、权限、同项目排队都不变。要改文件时，授权请求走现有转发：主聊天弹窗，绑定了手机就发到手机，回 1 允许。
5. 这一轮结束后职责被唤醒：重新读 PR 和 CI，核对验收标准。
   - 通过：「完成：PR #12 新提交 abc123 的 CI 全部通过（证据链接）」。
   - 没通过：说明现状，等下一次检查；连续几次没过就停下来问你。
6. PR 合并或关闭、预算用完、你暂停或取消，职责就结束。

## 怎么做（以复用为主）

| 部分 | 复用 | 新加 |
| --- | --- | --- |
| 存储、定时、租约、重试、去重、重启恢复 | `work-store.ts`、`work-scheduler.ts`（持续任务的队列） | 新的任务种类 `duty`：目标、来源、所属话题、验收标准、授权、提醒方式、预算 |
| 读 PR 和 CI | `research.ts`（只读、固定路径、无凭证） | — |
| 派单给话题 | DSH `/goal` 的轮次本来就"每一轮都进目标所在的话题"（`goalRoundOf`、`goalTopics`），派单走同一条路 | 一种 TheOne 自己的输入（`theone-duty`），直接进所属话题，不经过分类 |
| 先问再做 | 话题权限同步（`syncPermissions`）、授权转发到主聊天和手机（`forwardApprovals`、`remote-relay.ts`） | 职责回合把话题的权限临时设成"先问再做"，不管主聊天当前是什么模式 |
| 等待和唤醒 | 队列的 `waiting` 状态和按事件唤醒（`wake(id, eventId)`）；调度每次最多跑 60 秒，所以派单后不在调度里等 | 话题这一轮结束（`turn/end`）时唤醒对应职责 |
| 验收 | — | 能确定的直接判断（新提交上的 CI 通过）；需要模型判断的标明"未经验证" |
| 通知 | `deliverWorkNotice`（主聊天，持久、去重） | 绑定了手机入口时也发到手机 |
| 面板 | 「持续任务」面板 | 显示：检查中 / 已派给「某话题」/ 等你确认 / 已完成（附证据） |

## 按设计语言和 dot 的教训检查

- **说到做到。** 评测里 dot 最被诟病的是"先宣布后做到"。这里的"完成"只在验收核对通过后说，并附证据；派单、等待、失败都如实显示。
- **看得见。** 派出去的工作在主聊天里照常显示，话题能打开接手；面板能看到每件职责走到哪一步。
- **不越权。** 只有用户原话要求才创建（沿用持续任务的"引用原话"校验）；只能派给它所属的话题；默认先问再做；学到的东西不扩大权限。
- **少打扰。** 只在需要决定、完成、出新问题时找你。
- **只说话。** 创建、暂停、取消都能在聊天里说；面板只是另一个入口。

## 风险

- **真动手。** 可能改错代码。缓解：默认先问再做；同项目排队；有次数和时间上限；只用来源方给的信息，PR 标题和 CI 文本都当不可信资料。
- **没人回应授权。** 手机上 10 分钟不回按拒绝；主聊天的弹窗默认不超时，职责的回合需要一个超时（建议 30 分钟），超时就拒绝并通知。
- **花费。** 每次派单就是一个完整的话题回合。上限：每件职责最多派单几次（建议默认 3 次），超过就停下来问。
- **DSH 关着不跑。** 已知限制，和持续任务一样。

## 分步

1. [x] 持续任务的通知同时发到已绑定的手机（每个入口每条只发一次，主聊天重试不会重复；暂停的任务不发）。
2. 职责的数据结构；`theone_task` 能创建 `duty`（验收标准、授权、提醒、预算）。
3. 派单走 goal 轮次的路径进话题；职责回合用"先问再做"。
4. 回合结束唤醒、核对验收、汇报。
5. 面板显示职责状态。
6. 真实 DSH 里端到端检查（模拟 GitHub 和会改文件的测试模型），并开始记"职责完成率""说到做到率"。

## 要用户决定的

1. 职责回合的授权：固定"先问再做"，还是创建时可以选"直接做"？（建议第一版固定"先问再做"）
2. 授权没人回应：多久算超时、超时后怎么办？（建议 30 分钟，拒绝并通知）
3. 通知去哪：绑定了手机入口时，默认也发手机吗？（建议是）
4. 第一版只支持"GitHub PR"这一种来源，可以吗？（建议可以：现成、可验证、能完整演示）
